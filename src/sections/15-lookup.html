From shape to method: a lookup table

Given what you have, use this. Every row assumes you have already plotted a histogram and checked for censoring and bimodality, as in the reading-a-shape checklist.

Match the data to the tool

You would not weigh flour with a thermometer. Five kinds of eval data, five toolboxes.

Pass or fail on each task is a pile of coin flips. Report the rate with its count, give it a Wilson interval, and compare paired runs with McNemar.

Latency leans right with a long tail. Averages hide the bad days, so report percentiles and get their uncertainty from the bootstrap.

Counts like tool calls per session usually vary far more than their average would suggest (variance 11 against a mean of 4). Poisson tools will claim false precision; use quantiles or a negative binomial.

Star ratings are ordered labels, not measurements: the gap from 2 to 3 stars is not the gap from 4 to 5. Report the share of 4s and 5s and compare with rank tests.

Two humps or a spike at a cap means stop before you summarise. Split the populations, or report how many hit the wall. The table below lists every row.

Plain wordsPick the tool that fits the data

You would not measure flour with a thermometer. Each kind of eval data, yes/no results, waiting times, counts, star ratings, has tools that fit it and tools that quietly give wrong answers. This table matches each kind of data to a way of summarising it, a way of comparing two models, and a way of drawing an error bar.

For leadersUse the table as a review checklist

You do not need to run these methods yourself to use this table well. When a result lands in front of you, find the row that matches the metric and check the analysis against it.

  1. Was the comparison paired? If both models ran the same tasks, the comparison should use the pairing (McNemar, paired bootstrap). An unpaired test throws away most of the statistical power and can miss real wins.
  2. Does the interval method match the data? Wilson for rates, bootstrap for percentiles, cluster bootstrap for anything nested in sessions or conversations. A normal-approximation interval on a 98% pass rate or a session-level metric is a warning sign.
  3. Was the data split or flagged first? Mixtures need segmenting and censored data needs its censoring rate reported. If neither check is mentioned, ask.
  4. Is the summary the one users feel? Percentiles for latency, top-two-box for satisfaction, rates with counts for pass/fail.
Principal asks
"Which row of the table is this metric, and does the method match?" A team that can answer instantly has thought about its measurement. A pause usually means the default tool was used without checking whether it fits.
Under the hoodThe decision, compressed

The table encodes four questions asked in order:

  1. Is it binary, count, continuous, or ordinal? This fixes the family: binomial and beta for binary, Poisson or negative binomial for counts, lognormal or quantile methods for positive continuous data, rank methods for ordinal scores.
  2. Are observations independent? If they are nested (calls in sessions, turns in conversations), the effective sample size is closer to the number of clusters, and intervals must resample clusters.
  3. Are the comparisons paired? Shared tasks call for paired tests, which use within-task differences and remove between-task difficulty from the noise.
  4. Is the statistic smooth? Means and medians bootstrap well at moderate n. Extreme quantiles and maxima do not, and need more data, a parametric tail model, or an honest "insufficient data".
