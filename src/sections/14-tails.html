Long tails and outliers: error or product?

Latency, token counts, and agent loop lengths all have long tails, and every team eventually argues about what to do with the extreme values. The first question is never which technique. It is whether the outlier is an error or the product.

Plain wordsThe slow request is a real customer

If a restaurant serves most meals in ten minutes but one table waits an hour, that hour is not a typo. It is a customer who left angry. Deleting it from the spreadsheet makes the average look better and the restaurant no better. Only remove a value if you can show the measurement itself was broken, such as a clock error or a logging bug. Otherwise, change how you summarise, not what you measured.

Key idea
In eval data most long tails are signal. A 40 second response is something a real user actually waited through. Winsorizing it makes your chart prettier and your product no better. The honest default is to change the summary statistic, not the data.
Outlier handling, side by side
Add outliers and watch which estimators move. The median barely notices. The raw mean tracks the tail directly. Move the winsorization percentile and see how much the answer depends on a threshold somebody picked arbitrarily.

The options, in the order to try them

OptionWhat it doesConsUse when
1. Change the statisticReport p50, p95, p99 with bootstrap intervals instead of a meanNo single headline number; p99 unstable at small nThe tail is real user experience. Almost always, for latency
2. SegmentFind the variable that separates the tail into its own populationNeeds a plausible mechanism; you can fish until something separatesYou can name a candidate first. Highest value option and the most skipped
3. Log transformAnalyse on the log scale, report back in original unitsGeometric mean is not the arithmetic mean, so it cannot answer capacity or cost questions. Breaks on zerosData is roughly lognormal and you want to model it
4. WinsorizeCap values above a percentile at that percentileBiases the mean by an unknown amount; the cap point is arbitrary and two teams will pick differentlyYou have confirmed instrumentation errors, not slow requests
5. Trimmed meanDrop a fixed share from each end, average the restSymmetric trimming on an asymmetric tail removes real data from one side and nothing from the otherRarely right for a one sided tail
6. Robust estimatorsHuber, Hodges-Lehmann: downweight rather than deleteHarder to explain; tuning constants are another arbitrary choiceYou need a mean-like number that resists contamination
7. Rank based testsMann-Whitney instead of a t testNo longer a statement about means; effect sizes less intuitiveComparing two groups where outliers would flip a t test
8. Model the tailFit a generalized Pareto above a thresholdReal machinery, real assumptionsThe tail itself is the deliverable
Watch out
Check for censoring before any of this. A spike of values sitting exactly at your timeout means those are not measurements, they are lower bounds. No outlier technique fixes that, and every one of them will quietly make the bias worse.

Per metric

  • Latency: quantiles, never a mean. Segment by cold start and retry status first.
  • Token counts: log scale for analysis, quantiles for reporting. Watch for a bimodal split between short answers and agentic loops, which is segmentation, not outliers.
  • Tool calls per session: the tail is task difficulty, so it is signal. Negative binomial or quantiles. Never trim.
  • Pass rates: bounded at 0 and 1, so no tail. Different problem entirely.
Under the hoodWinsorized, trimmed, and geometric means
\[ \tilde{x}_i = \min\!\big(x_i,\ Q(0.99)\big) \qquad\qquad \bar{x}_\alpha = \frac{1}{n-2\lfloor \alpha n\rfloor}\sum_{i=\lfloor \alpha n\rfloor+1}^{n-\lfloor \alpha n\rfloor} x_{(i)} \]Left: winsorizing caps each value at the 99th percentile. Right: the \(\alpha\)-trimmed mean averages the sorted values \(x_{(i)}\) after dropping a share \(\alpha\) from each end.
\[ \text{GM} = \exp\!\left(\frac{1}{n}\sum \ln x_i\right) = \left(\prod x_i\right)^{1/n} \]The geometric mean: average on the log scale, then come back. On lognormal data it lands on the median.
import numpy as np
from scipy import stats

lat = np.concatenate([stats.lognorm.rvs(0.7, scale=2, size=995, random_state=7),
                      [45, 52, 61, 80, 120]])          # five real slow requests

def centres(x):
    x = np.asarray(x, dtype=float)
    cap = np.quantile(x, 0.99)
    return {
        "raw mean":        x.mean(),                    # moves with every outlier
        "median":          np.median(x),                # ignores them entirely
        "10% trimmed":     stats.trim_mean(x, 0.10),    # drops both tails
        "winsorized p99":  np.minimum(x, cap).mean(),   # caps rather than drops
        "geometric mean":  np.exp(np.log(x).mean()),    # centre on the log scale
        "p95":             np.quantile(x, 0.95),        # when the tail IS the point
    }

for k, v in centres(lat).items():
    print(k.ljust(16), round(v, 3))

# CENSORING CHECK FIRST. A pile-up at one value near the top means those
# are lower bounds, not measurements, and every method above is then biased.
top = lat[lat >= np.quantile(lat, 0.98)]
print("distinct values in the top 2%:", len(np.unique(np.round(top, 3))))
# If that comes back as 1 or 2, you have a timeout, not a tail.
For leadersOutlier policy is a product decision

How a team handles extreme values decides which users the metric speaks for. That choice should be explicit, written down, and fixed before results come in.

  • Pre-register the rule. If the winsorization threshold or exclusion criterion is chosen after seeing the data, it can be tuned (often unconsciously) to produce the desired answer. Two teams picking different cut-offs on the same data can report opposite conclusions.
  • Treat "we removed outliers" as a red flag until explained. Ask what was removed, how many, and what evidence shows each was a measurement error rather than a slow or failed run. In agent evals, the tail is often exactly the failures you most need to see.
  • Ask for the segment, not the trim. The highest-value response to a long tail is finding the variable that explains it: a task category, a tool, a context length bucket. That turns a statistics argument into a fixable engineering problem.
  • Separate cost questions from experience questions. Budgets need means (totals). Users experience percentiles. A report that uses one summary for both is answering one of the two questions wrongly.
Principal asks
"If we had not excluded anything, would the conclusion change?" Ask for both versions side by side. If the conclusion flips, the exclusion rule is carrying the result, and it needs much stronger justification than a footnote.
