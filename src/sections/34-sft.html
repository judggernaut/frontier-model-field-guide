Supervised fine-tuning: teaching the format

A pretrained model has read a large slice of the internet and can continue any text. It doesn't yet know that it is supposed to be an assistant. Supervised fine-tuning (SFT) shows it thousands of example conversations and trains it, with the same next-token loss used in pretraining, to produce the assistant's side. It is the first step of post-training and the base that preference tuning and RL build on.

What SFT actually changes

Plain wordsA well-read intern learning the house style

Picture a new hire who has read every book in the library but has never worked in an office. Ask them a question and they might answer, or they might write the next page of a novel, or ask you a question back. They know a lot. They just don't know the job.

SFT is the training binder: "Here is a question a customer asked. Here is exactly how we answer." After a few thousand of these, the intern answers in the right format, in the right tone, and knows when to say "I can't help with that." The binder teaches very little new knowledge. Mostly it teaches how to use the knowledge they already have.

For leadersSFT shapes behaviour cheaply. It rarely adds capability.

The LIMA paper (Zhou et al., 2023) fine-tuned a 65B model on only 1,000 carefully chosen examples and got responses that humans often preferred to those of much larger tuning efforts. The authors called this the superficial alignment hypothesis: almost all knowledge comes from pretraining, and SFT mostly selects which style and format to use. Later work showed it is only partly true. Format and persona do come cheaply. Reliable gains on hard skills such as math, code, and tool use need much more data, often hundreds of thousands to millions of examples, and usually RL afterwards.

Cheap to change with SFT

Response format, tone, persona, refusal style, following a chat template, calling tools in the right syntax.

Expensive to change with SFT

Factual knowledge, deep reasoning, robustness on hard problems. SFT can teach a model to sound like it reasons without reasoning better.

Usually the bottleneck

Data quality and coverage, not compute. A single SFT run on a frontier model is small next to pretraining.

The real risk

Quietly damaging capabilities the base model had. You only see it if you measure it.

Principal asks
  • What behaviour is this SFT run supposed to change, and which eval shows that change?
  • Which capabilities could it break, and is there a regression suite for them?
  • Who wrote the data, how was quality checked, and what fraction did a human actually read?
  • Are we teaching a skill, or teaching the model to imitate the surface of a skill?
Under the hoodSame loss, different data, a masked sum

SFT minimises the conditional negative log likelihood of the response \(y\) given the prompt \(x\), over a dataset of demonstrations \(\mathcal{D}\):

\[ \mathcal{L}_{\text{SFT}}(\theta) = -\,\mathbb{E}_{(x,y)\sim\mathcal{D}} \left[ \frac{1}{|y|}\sum_{t=1}^{|y|} \log p_\theta\!\left(y_t \mid x, y_{<t}\right) \right] \]Identical to the pretraining objective, except the sum runs only over response tokens \(y_t\). The prompt \(x\) is context, not a target.

Viewed as imitation learning, SFT is behaviour cloning: the model learns to copy the demonstrator's action at each step, always conditioned on the demonstrator's own previous tokens. That is called teacher forcing. At inference the model conditions on its own previous tokens, so small errors can compound into states the training data never covered. This exposure bias is one reason on-policy methods (RL, on-policy distillation) often help after SFT.

Chat templates and special tokens

Plain wordsStage directions in a script

A play script marks who is speaking: HAMLET:, OPHELIA:. A chat model needs the same thing. Special markers wrap each turn so the model knows where the user stops, where it should start talking, and when to stop. Get the markers wrong and the model gets confused, like an actor reading someone else's lines.

For leadersTemplate mismatches cause silent, expensive bugs

The template is a contract between training, serving, and evaluation. If the eval harness formats prompts differently from training (a missing system turn, a different end-of-turn token, an extra newline), scores can drop several points with no change to the model. It is one of the first things to check when an eval result looks wrong.

Watch out
Common template bugs: the end-of-turn token is never trained, so the model rambles past its answer; the tokenizer adds a second beginning-of-sequence token; tool-call turns use a role the serving stack doesn't know; the eval harness applies the base model's template to the chat model.
Under the hoodWhat a formatted conversation looks like

Templates differ by model family. A ChatML-style layout (illustrative) looks like this:

<|im_start|>system
You are a concise assistant.<|im_end|>
<|im_start|>user
What is 17 * 3?<|im_end|>
<|im_start|>assistant
51<|im_end|>

The special markers are single tokens, either reserved in the pretraining vocabulary (as in Llama 3) or added before SFT; only when they are new are their embeddings learned during SFT. In Hugging Face tooling the template is stored with the tokenizer as a Jinja string and applied with tokenizer.apply_chat_template. Use the same function in training, serving, and the eval harness, and check a rendered example in each by eye.

Loss masking: which tokens teach

Plain wordsGrade the answer, not the question

When you mark a student's exam you grade what they wrote, not the printed questions. SFT works the same way. The model reads the whole conversation, but it is only graded on the assistant's words. Otherwise it would spend effort learning to write user questions, which isn't its job.

For leadersA one-line choice that changes what the model learns

Masking decides what behaviour you are paying to teach. Training on user turns teaches the model to imitate users, which can leak into answers that start interviewing the user back. Training on tool outputs teaches it to hallucinate tool results instead of waiting for them. Training only on the final turn of a multi-turn conversation wastes most of the data. Most teams default to "all assistant turns, never tool or environment output," and treat any change as an experiment with its own eval.

Under the hoodLabels of -100

In PyTorch, CrossEntropyLoss ignores label positions set to -100 by default. Masking is done by copying the input ids into labels and overwriting non-target spans:

import torch

IGNORE = -100  # CrossEntropyLoss(ignore_index=-100) skips these positions

def build_labels(input_ids, spans):
    """spans: list of (start, end, role) over token positions.
    Only assistant tokens, including the end-of-turn token, become targets."""
    labels = torch.full_like(input_ids, IGNORE)
    for start, end, role in spans:
        if role == "assistant":
            labels[start:end] = input_ids[start:end]
    return labels

ids = torch.arange(12)                       # stand-in token ids
spans = [(0, 4, "system"), (4, 7, "user"), (7, 12, "assistant")]
print(build_labels(ids, spans))
# tensor([-100, -100, -100, -100, -100, -100, -100,    7,    8,    9,   10,   11])

One detail with real consequences: the loss is usually averaged over target tokens in the batch. Long responses then get more total weight than short ones. Some recipes average per sequence first, so every example counts equally. Neither is wrong, but changing it shifts the model toward or away from long answers.

Packing and attention masking

Plain wordsFilling the moving van

GPUs process fixed-length rows. Short conversations leave most of a row empty, like a moving van carrying one chair. Packing puts several conversations end to end in one row so nothing is wasted. The catch: you have to put up walls between them so one conversation can't peek at another.

For leadersThroughput versus correctness

Packing can cut SFT compute by 2× or more when examples vary in length. Without proper attention masking, though, tokens in conversation B can attend to conversation A. That is a subtle form of contamination inside the training batch, and it can teach the model to draw on context that won't exist at inference. Ask whether the training stack uses per-document attention masks (often done with variable-length attention kernels) and resets position ids per document.

Under the hoodBlock-diagonal causal masks

With packing, the attention mask becomes block diagonal: causal within each document, zero across documents. Implementations pass cumulative sequence lengths (for example cu_seqlens in FlashAttention's variable-length API) instead of materialising a full mask. Position ids restart at 0 for each document so rotary embeddings see the same positions they would without packing.

Data: quality, quantity, and mix

Plain wordsYou become what you imitate

The model will copy whatever is in the examples, including mistakes, padding, and bad habits. A thousand excellent examples can beat a hundred thousand sloppy ones. And if every example is about cooking, the model gets worse at everything else.

For leadersWhere SFT budgets actually go
  • Quality filtering often beats collecting more. Remove wrong answers, refusals of fine requests, and answers that hedge or pad. Each one teaches a habit.
  • Diversity of tasks, formats, and difficulty matters more than raw count. Open recipes such as Tülu 3 (Lambert et al., 2024) mix general chat, math, code, safety, multilingual, and instruction-following sets, and tune the mixture against a broad eval suite.
  • Mixture weights are hyperparameters. Upweighting one skill steals capacity from others. Run ablations, not intuition.
  • Human versus synthetic data. Most modern SFT data is model-generated and filtered (see distillation and synthetic data). Human data stays essential for the hardest tasks, for safety, and for checking that synthetic data isn't drifting.
  • Multi-turn and tool-use data must include realistic failures: tool errors, ambiguous requests, users changing their minds. A model trained only on clean single-turn data breaks in real agent traces.
Watch out
SFT data written by a stronger model teaches the student to sound like that model, confidence included. If the teacher states things it can't verify, the student learns to hallucinate in the same voice. Fluency goes up faster than accuracy, and judge-based evals reward fluency.

Epochs, overfitting, and forgetting

Plain wordsMemorising the binder, forgetting the library

Read the training binder once and you learn the style. Read it ten times and you start reciting the exact examples word for word, which doesn't help with new questions. Worse, if the binder only covers a few topics, the intern can start forgetting things they knew before. That is catastrophic forgetting.

For leadersPick checkpoints with evals, not loss

Typical SFT runs 1 to 3 epochs. Validation loss often starts rising after the first or second epoch while downstream scores keep improving for a while, because the model gets more decisive about format. So validation loss alone is a poor stopping rule. Teams save several checkpoints and choose with a broad eval suite.

Forgetting is the cost leaders most often miss. Narrow SFT, such as a single domain or one customer's format, can reduce general reasoning, safety behaviour, or multilingual ability. Standard mitigations are mixing in general instruction data (replay), lower learning rates, fewer epochs, and LoRA, which tends to forget less because it changes fewer directions in weight space.

Under the hoodWhy validation loss and quality diverge

Cross-entropy on a held-out set penalises confident wrong tokens heavily. As SFT sharpens the output distribution (lower entropy), a few confidently wrong tokens on held-out examples can raise the average loss even while greedy outputs get better. Loss measures calibration of the whole distribution; quality metrics usually look at one sampled or greedy answer. Report both and expect them to disagree after the first epoch.

To detect forgetting, evaluate the base model and every candidate checkpoint on the same frozen general suite, and test the difference with a paired method from Part II, since the items are shared.

Evaluating an SFT run

Eval lens

Held-out loss is necessary but not enough. A credible SFT evaluation has four parts:

  1. Target behaviour. The thing the run was meant to change: format adherence, tool-call validity, refusal accuracy, domain task pass rate. Measure it with intervals.
  2. Capability regression suite. A fixed, broad set (reasoning, code, math, knowledge, multilingual, safety) compared against the parent checkpoint with paired tests. Any drop beyond noise is a finding.
  3. Pairwise win rate against the previous model on realistic prompts, judged by humans or a validated LLM judge, with position swapping and length control.
  4. Contamination check. Synthetic SFT data can contain benchmark items the teacher saw. Run n-gram and embedding overlap against every eval set (see contamination).
Principal asks
  • What did the base model score on the regression suite, and what is the paired delta with an interval?
  • Did win rate go up because answers got better, or because they got longer?
  • Which checkpoint did we pick, and was it chosen on the same data we are now reporting? (If so, the number is optimistically biased.)
  • If we removed the 10% lowest-quality examples, would the result change?
