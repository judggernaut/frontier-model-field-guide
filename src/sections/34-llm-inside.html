Inside an LLM: it only ever predicts the next token

Strip away the chat window, the persona and the tools, and a large language model does one thing: given some text, it outputs a probability for every possible next token. Generation is that one prediction run in a loop. This chapter walks the pipeline from text to prediction, part by part, so the rest of the guide (assistants, reasoning, evals) rests on a concrete picture. Tokenization and the training loss are covered in Pretraining; how the next token is chosen is covered in Inference.

Your phone keyboard, a few hundred times in a row

Generation as autocomplete on repeat, in five pictures.

Your phone keyboard watches what you type and offers three guesses for the next word. It learned those guesses from lots of other people's messages.

Tap the middle guess over and over and a sentence appears, one word per tap. A phone keyboard only looks at the last word or two, so it soon loops back to "gym".

An LLM plays the same game with a far better guesser. It reads the whole message so far and gives every token in its vocabulary a probability (numbers illustrative).

Pick one token, glue it onto the text, and feed the longer text back in. That loop is the whole of generation. A 500-word answer is roughly 650 laps, because a word averages about 1.3 tokens in English.

The rest of this chapter opens the box. Every part of it, however clever, exists to produce one thing: a probability for each possible next token.

The one job: predict the next token

Plain wordsA very well-read autocomplete

Imagine someone who has read a large share of the public internet, many books and a lot of code, and has played one game the whole time: cover the next word, guess it, check, adjust. After trillions of rounds they become uncannily good at it. To guess the next word in a physics textbook well, you have to have picked up some physics. To guess the next line of a program, you need to follow what the program does.

That is a language model. When it "answers" you, it is guessing the next small piece of text (a token, roughly three quarters of a word in English), adding it to the page, and guessing again. There is no separate answering mode. Everything you see comes out of that loop.

For leadersWhy the framing matters for decisions

"It only predicts the next token" is accurate about the interface and says little about the capability. Both halves have consequences:

  • Cost and latency scale with output length. Every generated token is a full pass through the model. Long answers and long chains of reasoning cost proportionally more compute and time.
  • Behaviour is shaped by the text it is given. Prompts, system prompts, retrieved documents and tool outputs all work the same way: they are more text the prediction is conditioned on. See From predictor to assistant.
  • Errors are fluent. The model is trained to produce likely text. Likely and true usually coincide, but when they diverge you get confident, well-phrased mistakes.
  • The interface is a probability distribution. That makes outputs random unless decoding is greedy, and it gives you log-probabilities you can use for scoring, routing and calibration.
Under the hoodThe autoregressive factorization

Any probability over sequences can be written as a product of next-token conditionals. A language model with parameters \(\theta\) learns each factor:

\[ P_\theta(x_1, \dots, x_T) = \prod_{t=1}^{T} P_\theta(x_t \mid x_1, \dots, x_{t-1}) \]\(x_t\) is the token at position \(t\). One network computes every factor; it sees only positions before \(t\) when predicting \(x_t\).

Training minimises the cross-entropy \(-\log P_\theta(x_t \mid x_{<t})\) averaged over trillions of positions (Pretraining). Because of the causal mask (below), one forward pass over a training sequence of length \(T\) yields \(T\) predictions at once, which is why training is parallel while generation is sequential. Generation samples \(x_{t+1} \sim P_\theta(\cdot \mid x_{\le t})\), appends it, and repeats until an end-of-sequence token or a length limit.

Key idea
A language model is a function from a token sequence to a probability distribution over the next token. Everything else (chat, tool calls, reasoning traces, refusals) is text produced by calling that function in a loop.

One trip through the model

From "The cat sat on the" to "mat", in six pictures.

Step 1. A tokenizer cuts the text into pieces called tokens and swaps each for an ID number. Note the leading spaces: "␣cat" and "cat" are different tokens. (Details in Pretraining.)

Step 2. Each token ID looks up a row in a big table and becomes a vector: a long list of numbers. Training arranges these so that tokens used in similar ways end up near each other, like neighbourhoods on a map.

Step 3. The vectors travel up through a stack of identical blocks. In each block, attention lets every position gather information from earlier positions, and an MLP transforms what each position holds. Each block adds its result to a running total, the residual stream.

Step 4. Only the vector at the last position matters for the next token. One matrix multiply turns it into a score, called a logit, for every token in the vocabulary (numbers illustrative).

Step 5. Softmax turns the scores into probabilities. The decoder then picks one token, either the most likely or a weighted random draw. How it picks is a setting, covered in Inference.

Step 6. Append the new token and run the whole stack again on the longer text. One forward pass per token, every time. That is all generation is.

Tokens and embeddings: words become points on a map

Plain wordsEvery word gets an address

Computers cannot do arithmetic on words, so each token is replaced by a long list of numbers, its embedding. Think of it as an address on an enormous map with thousands of directions instead of two. Training moves the addresses around until words used in similar ways live in the same neighbourhood: "cat" near "kitten" and "dog", "Paris" near "Rome" and "Berlin". Nobody draws this map. It falls out of the guessing game, because words that can replace each other in a sentence help predict the same next words.

For leadersWhat the tokenizer and embedding table decide

The tokenizer is fixed before pretraining and is expensive to change afterwards, because every learned weight assumes it. It decides how many tokens a page costs (pricing, context length and latency are all counted in tokens), and it decides fairness across languages: text in scripts the tokenizer handles poorly can take several times more tokens for the same content, which means higher cost and a shorter effective context. The embedding table and the matching output table hold one row per vocabulary entry, so a 128K-entry vocabulary at width 8,192 is about a billion parameters each. Tokenizer choices and their trade-offs are in Pretraining.

Under the hoodLookup, position, similarity

The embedding layer is a matrix \(E \in \mathbb{R}^{V \times d}\). Token ID \(i\) selects row \(E_i\), the first vector on the residual stream. Similarity between two embeddings is usually measured by cosine:

\[ \cos(u, v) = \frac{u \cdot v}{\lVert u \rVert\, \lVert v \rVert} \]1 means the same direction, 0 unrelated, −1 opposite. Classic word vectors (Mikolov et al. 2013) famously gave king − man + woman ≈ queen; modern contextual models make the picture richer, since a token's vector changes layer by layer with context.

Attention by itself ignores order: shuffle the inputs and each position computes the same thing. Order is injected with positional information. Most current open models use rotary position embeddings (RoPE), which rotate query and key vectors by an angle proportional to position so that their dot product depends on the distance between tokens.

Attention: each position looks back at earlier ones

Who is "it"? Attention as a quick look back

Queries, keys, values and the causal mask, with one sentence.

Reading "The cat sat on the mat because it", the model has to work out what "it" means before it can guess the next word. A word on its own cannot know that. It has to look back.

Every word holds up a label describing itself, called its key. The current word holds up a question, its query. Real keys and queries are vectors the model learned, so these word labels are only a sketch.

Compare the question with every label, including its own, by multiplying the two vectors (a dot product). A high score means a good match. "cat" scores 3.0, "mat" 1.6, filler words near zero.

Softmax turns the scores into weights that add to 100%: 58% on "cat", 14% on "mat", 8% on itself, a little everywhere else. These weights are the attention pattern.

Each word also carries a value: the information it hands over. "it" receives a blend weighted by attention, so it now carries a lot of "cat". Words after it are hidden by the causal mask: when the model writes "it", they do not exist yet.

Plain wordsA librarian with sticky notes

Picture a library where every book on the shelf has a label on its spine and some content inside. You walk in with a question. You compare your question with each label, pull the books whose labels match best, and read mostly from those, a little from the rest. In attention, the question is the query, the spine labels are keys, and the contents are values.

Every word in the text does this at once, at every layer, and with many different questions in parallel (one per head): "what does this pronoun refer to?", "what was the previous word?", "is there an open bracket I should close?". One rule holds throughout: a word may only look at words that came before it. The future has not been written yet.

For leadersWhy attention drives cost and context limits

Attention is how information moves between positions, so it is what makes long documents, multi-turn chats and retrieval work. It is also the part whose cost grows with context: every new token compares itself with every earlier token, so the work per token grows with the length of the conversation, and a full pass over a long prompt grows with its square. To avoid recomputing the past, servers store each earlier token's keys and values in a KV cache, which trades compute for memory and is often what limits how many users one machine can serve (Inference).

Long context windows are an engineering claim about memory and speed. Whether the model actually uses information deep in the context is a separate empirical question that needs its own evals.

Under the hoodScaled dot-product attention with a causal mask

Each position's residual vector \(h\) is projected three ways: \(q = W_Q h\), \(k = W_K h\), \(v = W_V h\). Stack them for all positions into matrices \(Q, K, V\):

\[ \mathrm{Attn}(Q, K, V) = \mathrm{softmax}\!\left(\frac{Q K^{\top}}{\sqrt{d_k}} + M\right) V, \qquad M_{ij} = \begin{cases} 0 & j \le i \\ -\infty & j > i \end{cases} \]Row \(i\) of \(QK^\top\) scores position \(i\)'s query against every key. Dividing by \(\sqrt{d_k}\) keeps scores from growing with vector width, which would push softmax into near one-hot outputs with tiny gradients. The mask \(M\) sends future positions to \(-\infty\), so their weight after softmax is exactly 0.

Worked mini example. Three tokens, "cat sat it", with hand-picked two-dimensional vectors (\(d_k = 2\), so we divide by \(\sqrt 2 \approx 1.414\)). Take the row for "it":

Key tokenkey \(k\)value \(v\)\(q \cdot k\) with \(q = (1.5, 0.5)\)÷ √2softmax weight
cat(2, 0)(1, 0)3.02.1210.601
sat(0, 1)(0, 1)0.50.3540.103
it(1, 1)(0.5, 0.5)2.01.4140.296

The output for "it" is the weighted sum of values: \(0.601(1,0) + 0.103(0,1) + 0.296(0.5,0.5) = (0.749, 0.251)\), mostly "cat". For the row "sat", the mask hides "it", so "sat" splits its attention between "cat" and itself; the row for "cat" can only see itself and puts weight 1.0 there. The code computes all three rows.

import math

def softmax(scores):
    m = max(scores)                       # subtract the max so exp never overflows
    e = [math.exp(s - m) for s in scores]
    total = sum(e)
    return [x / total for x in e]

def causal_attention(Q, K, V):
    """Q, K, V: one row per token. Returns (weights, outputs)."""
    d = len(K[0])
    weights, outputs = [], []
    for i, q in enumerate(Q):
        # score every token; tokens after i are masked to -inf (they have not been written yet)
        scores = [sum(a * b for a, b in zip(q, k)) / math.sqrt(d) if j <= i else -math.inf
                  for j, k in enumerate(K)]
        w = softmax(scores)
        out = [sum(w[j] * V[j][c] for j in range(len(V))) for c in range(len(V[0]))]
        weights.append(w)
        outputs.append(out)
    return weights, outputs

fn softmax(scores: &[f64]) -> Vec<f64> {
    let m = scores.iter().cloned().fold(f64::NEG_INFINITY, f64::max); // subtract the max so exp never overflows
    let e: Vec<f64> = scores.iter().map(|s| (s - m).exp()).collect();
    let total: f64 = e.iter().sum();
    e.iter().map(|x| x / total).collect()
}

/// Q, K, V: one row per token. Returns (weights, outputs).
fn causal_attention(q: &[Vec<f64>], k: &[Vec<f64>], v: &[Vec<f64>]) -> (Vec<Vec<f64>>, Vec<Vec<f64>>) {
    let d = k[0].len() as f64;
    let (mut weights, mut outputs) = (Vec::new(), Vec::new());
    for (i, qi) in q.iter().enumerate() {
        // score every token; tokens after i are masked to -inf (they have not been written yet)
        let scores: Vec<f64> = k.iter().enumerate().map(|(j, kj)| {
            if j <= i { qi.iter().zip(kj).map(|(a, b)| a * b).sum::<f64>() / d.sqrt() } else { f64::NEG_INFINITY }
        }).collect();
        let w = softmax(&scores);
        let out: Vec<f64> = (0..v[0].len()).map(|c| (0..v.len()).map(|j| w[j] * v[j][c]).sum()).collect();
        weights.push(w);
        outputs.push(out);
    }
    (weights, outputs)
}

fn r3(x: &[f64]) -> Vec<f64> { x.iter().map(|v| (v * 1000.0).round() / 1000.0).collect() }

    // tokens: "cat", "sat", "it"   (2-dimensional toy vectors, chosen by hand)

    let k = vec![vec![2.0, 0.0], vec![0.0, 1.0], vec![1.0, 1.0]]; // what each token offers as a label
    let v = vec![vec![1.0, 0.0], vec![0.0, 1.0], vec![0.5, 0.5]]; // what each token hands over if chosen

    }

}

Multi-head attention runs \(H\) of these in parallel with separate projections of width \(d_k = d/H\), concatenates the outputs and mixes them with \(W_O\). Heads specialise. Interpretability work has found heads that copy the previous token, "induction heads" that complete repeated patterns (Olsson et al. 2022), and heads that park most of their weight on the first token when nothing else is relevant (the "attention sink", Xiao et al. 2023).

MLP layers and the residual stream: where features live

Plain wordsA shared whiteboard and a room of specialists

Picture each word with its own whiteboard. The whiteboard travels up through the floors of a building. On each floor, two things happen. First, the word glances at the whiteboards of earlier words and copies over anything useful (attention). Then a room of specialists reads the board and adds notes: one recognises "this is a city name", another adds "Paris goes with France", another notices "we are inside a quotation". Nobody erases anything; everyone writes on top. That running whiteboard is the residual stream, and the specialists are the MLP layers.

By the top floor, the whiteboard for the last word holds everything needed to guess the next one.

For leadersWhere the parameters, and the facts, sit

In a standard dense transformer about two thirds of the parameters are in the MLP layers, and that is where much of the model's stored association ("Eiffel Tower" goes with "Paris") appears to live. That has practical consequences. Mixture-of-experts models replace the single MLP with many expert MLPs and route each token to a few of them, which buys more stored capacity per unit of compute. Knowledge editing methods target specific MLP weights. And because facts are spread through weights instead of stored as records, there is no row you can delete to make a model forget something, which matters for privacy and licensing requests.

Under the hoodThe block equations

A pre-norm transformer block updates the residual stream \(h\) for every position:

\[ h \leftarrow h + \mathrm{Attn}\big(\mathrm{LN}(h)\big), \qquad h \leftarrow h + \mathrm{MLP}\big(\mathrm{LN}(h)\big), \qquad \mathrm{MLP}(x) = W_2\, \phi(W_1 x) \]LN is layer normalisation (often RMSNorm). \(W_1\) widens from \(d\) to about \(4d\), \(\phi\) is a nonlinearity (GELU, or a gated SwiGLU in most current models), \(W_2\) projects back to \(d\). Each sublayer adds to \(h\); nothing overwrites it.

The additive structure is why Elhage et al. (2021) describe the residual stream as a shared communication channel: every layer reads from it and writes into it, and later layers can read what any earlier one wrote. Geva et al. (2021) showed that MLP layers behave like key-value memories, where rows of \(W_1\) detect input patterns and the matching columns of \(W_2\) write associated output directions. Meng et al. (2022, ROME) located factual associations in mid-layer MLPs of GPT-style models and edited single facts by changing one weight matrix.

Parameter count. Per layer, attention has four \(d \times d\) matrices (\(4d^2\)) and the MLP has two \(d \times 4d\) matrices (\(8d^2\)), so a layer is about \(12 d^2\). With \(d = 8{,}192\) and \(L = 80\) layers that is \(12 \times 8192^2 \times 80 \approx 64\) billion, plus roughly 2 billion for input and output embeddings at a 128K vocabulary: the shape of a 70B-class model (real models adjust these ratios with grouped-query attention and gated MLPs).

From vector to word: logits, softmax, and the pick

Plain wordsA scoreboard for every word

At the top of the stack, the model turns the last word's whiteboard into a score for every token it knows, often more than 100,000 of them. High score means "likely next". Softmax converts the scores into percentages that add up to 100. Then one token is picked: always the top one, or a random draw that favours the high scorers. That choice is a dial, set at serving time.

For leadersDecoding is a product decision

The same model gives different products under different decoding settings: deterministic and repetitive under greedy decoding, more varied and more error-prone at high temperature. Those settings are part of what you ship and part of what you evaluate. If an eval runs at temperature 0 and production runs at 0.8, the eval measured a different system. Settings and their trade-offs are in Inference.

Under the hoodUnembedding and softmax
\[ z = W_U\, \mathrm{LN}(h_T) \in \mathbb{R}^{V}, \qquad p_i = \frac{e^{z_i / \tau}}{\sum_{j=1}^{V} e^{z_j / \tau}} \]\(h_T\) is the final residual vector at the last position, \(W_U\) the unembedding matrix (sometimes tied to \(E^\top\)), \(z\) the logits, \(\tau\) the temperature. \(\tau \to 0\) approaches greedy argmax; \(\tau = 1\) is the trained distribution.

Softmax depends only on differences between logits, so adding a constant to every logit changes nothing; subtracting the max before exponentiating keeps it numerically safe (the code above does this). In the widget below, a counting model built in your browser replaces the transformer, but the interface is identical: context in, distribution out, pick, append. The snippet shows the same loop in a few lines. Note what greedy decoding does: with a model that only sees one word of context it falls into a loop, the same failure the phone keyboard showed.

from collections import Counter, defaultdict

corpus = ("the cat sat on the mat . the dog sat on the rug . "
          "the cat ate the fish . the dog ate the bone . the cat is happy .").split()

# count which word follows which: this table is the whole "model"
follow = defaultdict(Counter)
for prev, nxt in zip(corpus, corpus[1:]):
    follow[prev][nxt] += 1

def next_probs(word):
    c = follow[word]
    total = sum(c.values())
    return sorted(((w, n / total) for w, n in c.items()), key=lambda t: (-t[1], t[0]))

def lcg(seed):
    # tiny shared PRNG so Python and Rust draw the same numbers
    while True:
        seed = (seed * 1103515245 + 12345) % 2**31
        yield seed / 2**31

def generate(start, n, greedy=True, seed=7):
    out, rand = [start], lcg(seed)
    for _ in range(n):                      # one prediction per new token: the autoregressive loop
        probs = next_probs(out[-1])
        if greedy:
            out.append(probs[0][0])         # always take the most likely word
        else:
            r, acc = next(rand), 0.0
            for w, p in probs:              # walk the cumulative distribution
                acc += p
                if r < acc:
                    out.append(w)
                    break
            else:
                out.append(probs[-1][0])
    return " ".join(out)

print([(w, round(p, 3)) for w, p in next_probs("the")])  # [('cat', 0.333), ('dog', 0.222), ('bone', 0.111), ...]
print(generate("the", 6))                 # the cat ate the cat ate the   (greedy loops; ties go alphabetical)
print(generate("the", 6, greedy=False))   # the bone . the fish . the
use std::collections::HashMap;

/// count which word follows which: this table is the whole "model"
fn build(corpus: &[&str]) -> HashMap<String, HashMap<String, u32>> {
    let mut follow: HashMap<String, HashMap<String, u32>> = HashMap::new();
    for pair in corpus.windows(2) {
        *follow.entry(pair[0].to_string()).or_default().entry(pair[1].to_string()).or_default() += 1;
    }
    follow
}

fn next_probs(follow: &HashMap<String, HashMap<String, u32>>, word: &str) -> Vec<(String, f64)> {
    let c = &follow[word];
    let total: u32 = c.values().sum();
    let mut v: Vec<(String, f64)> = c.iter().map(|(w, n)| (w.clone(), *n as f64 / total as f64)).collect();
    v.sort_by(|a, b| b.1.partial_cmp(&a.1).unwrap().then(a.0.cmp(&b.0)));
    v
}

struct Lcg(u64);
impl Lcg {
    // tiny shared PRNG so Python and Rust draw the same numbers
    fn next(&mut self) -> f64 {
        self.0 = (self.0 * 1103515245 + 12345) % (1u64 << 31);
        self.0 as f64 / (1u64 << 31) as f64
    }
}

fn generate(follow: &HashMap<String, HashMap<String, u32>>, start: &str, n: usize, greedy: bool, seed: u64) -> String {
    let mut out = vec![start.to_string()];
    let mut rand = Lcg(seed);
    for _ in 0..n { // one prediction per new token: the autoregressive loop
        let probs = next_probs(follow, out.last().unwrap());
        if greedy {
            out.push(probs[0].0.clone()); // always take the most likely word
        } else {
            let (r, mut acc) = (rand.next(), 0.0);
            let mut pick = probs.last().unwrap().0.clone();
            for (w, p) in &probs { // walk the cumulative distribution
                acc += p;
                if r < acc { pick = w.clone(); break; }
            }
            out.push(pick);
        }
    }
    out.join(" ")
}

fn main() {
    let text = "the cat sat on the mat . the dog sat on the rug . \
                the cat ate the fish . the dog ate the bone . the cat is happy .";
    let corpus: Vec<&str> = text.split_whitespace().collect();
    let follow = build(&corpus);
    let p: Vec<String> = next_probs(&follow, "the").iter().map(|(w, p)| format!("('{}', {})", w, (p * 1000.0).round() / 1000.0)).collect();
    println!("[{}]", p.join(", ")); // [('cat', 0.333), ('dog', 0.222), ('bone', 0.111), ...]
    println!("{}", generate(&follow, "the", 6, true, 7));  // the cat ate the cat ate the   (greedy loops; ties go alphabetical)
    println!("{}", generate(&follow, "the", 6, false, 7)); // the bone . the fish . the
}

What "knowledge" means here

Plain wordsKnowing as being good at guessing

The model has no encyclopedia inside it and no list of sources. When it "knows" that the capital of Australia is Canberra, that means the weights make "Canberra" a very likely continuation of "The capital of Australia is". Facts that appeared thousands of times in training are reliable. Facts that appeared once or twice are shaky, and the model has no built-in signal telling it which is which. It will continue the sentence either way.

It is a bit like a friend who has read widely and answers from memory. Usually right on well-known things, and sometimes confidently mixing up two similar names on obscure ones.

For leadersImplications for products and evals
  • Long-tail facts are weak. Kandpal et al. (2023) found question-answering accuracy rises steeply with how many pretraining documents mention the relevant entities. Rare entities, recent events and internal company facts need retrieval or tools, not hope.
  • Knowledge has a date. Weights freeze at the training cutoff. Anything newer must come in through the context.
  • Knowledge is directional and phrasing-sensitive. Berglund et al. (2023, "The Reversal Curse") showed models trained on "A is B" often fail to answer "who is B?". A fact being "in the model" depends on how you ask.
  • Confidence is not provenance. The model cannot cite where a fact came from unless sources are in its context. See From predictor to assistant for hallucination and calibration.
Under the hoodKnowledge as compression

Minimising cross-entropy on a huge corpus rewards any internal structure that predicts text better: grammar, world facts, arithmetic procedures, the style of a particular author. A model with \(N\) parameters cannot memorise trillions of tokens verbatim, so it is pushed to store regularities that generalise and to keep exact strings only when they recur often (licences, famous quotes, boilerplate code). Mechanistic work supports a picture in which early layers build up a representation of the subject ("Eiffel Tower"), mid-layer MLPs add associated attributes into the residual stream, and attention heads move the relevant attribute to the position where the answer is predicted (Meng et al. 2022; Geva et al. 2023). That retrieval can fail silently, which is one root of hallucination.

Why long answers take time

Plain wordsOne word, one full trip

Reading your question is fast, because the model can process all of it in parallel. Writing the answer is slow, because each new token needs a complete trip through every layer, and the trip for token 51 cannot start until token 50 is chosen. A 1,000-token answer is 1,000 trips. That is why replies stream out word by word, and why a model that "thinks" for 10,000 tokens before answering takes a while.

For leadersThe two latencies

Serving has two phases with different economics. Prefill processes the prompt in parallel and sets the time to first token. Decode generates tokens one at a time and sets the time per output token. Long prompts mostly cost prefill compute; long answers and reasoning traces mostly cost decode time. Output tokens are usually priced several times higher than input tokens for this reason. When a team proposes "let the model think longer", the question is how many extra decode tokens the quality gain costs.

Watch out
"It only predicts the next token" is often used to mean "so it cannot plan or reason". That does not follow. Producing a good next token can require computing a lot internally. Anthropic's interpretability work on Claude 3.5 Haiku (Lindsey et al. 2025, "On the Biology of a Large Language Model") found the model choosing a rhyme word before writing the line that ends in it. The opposite mistake is just as common: treating fluent text as evidence of understanding or truth. Judge capability with evals, not with either slogan.
Under the hoodCompute, memory bandwidth, and the KV cache

A forward pass costs about \(2N\) floating-point operations per token for a dense model with \(N\) parameters (one multiply and one add per weight). Without a cache, generating token \(t\) would recompute keys and values for all \(t-1\) earlier tokens. The KV cache stores them, so each decode step computes only the new token and reads the cache:

\[ \text{KV bytes per token} = 2 \times L \times n_{\text{kv}} \times d_{\text{head}} \times \text{bytes per value} \]The 2 is one key and one value; \(L\) layers; \(n_{\text{kv}}\) key-value heads (fewer than query heads under grouped-query attention); \(d_{\text{head}}\) head width.

At small batch sizes, decoding is limited by memory bandwidth more than arithmetic: every step must stream all the weights through the chips. Illustratively, reading 140 GB of 16-bit weights for a 70B model across two GPUs at 3.35 TB/s each (6.7 TB/s aggregate) takes about 21 ms, so a single sequence cannot decode much faster than about 48 tokens per second on that hardware however fast the arithmetic is. Batching many users shares each weight read, which is why throughput and per-user speed trade off. Details, including speculative decoding, are in Inference.

Eval lens
Because the model's raw output is a probability distribution, there are two ways to score it, and they measure different things. Likelihood scoring compares the log-probability of each answer option (the classic multiple-choice harness): cheap, deterministic, but sensitive to tokenization and leading spaces, and it never looks at what the model would actually write. Generative scoring lets the model write an answer and grades it: closer to what users see, but random under sampling, so you need several samples and an interval (Statistics for eval sets). The two can rank models differently. State which one a number came from, at which temperature, with which prompt template.
Principal asks
Is this benchmark number from log-likelihood scoring or from generated answers, and at what temperature? How much of the latency budget is prefill versus decode for our median request? When the model gets a fact wrong, is it a missing fact (needs retrieval), a retrieval failure inside the model (sensitive to phrasing), or a decoding issue (right answer was likely but not picked)?
