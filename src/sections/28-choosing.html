Which metric or test, when

This chapter is a decision guide. It pulls together the metrics from classification and judges and the tests from statistics for eval sets and intervals and the bootstrap. For "my data has this shape, which method fits," use the lookup in from shape to method.

Plain wordsPick the metric by the question you are asking

Every metric answers a different question. "When it says yes, is it right?" is precision. "Did it find them all?" is recall. "Does it rank good above bad?" is AUC. "Is this difference real or luck?" is a statistical test. Start from the question, then pick the number. Picking the number first and inventing the question afterwards is how dashboards end up misleading people.

For leadersThe metric pack for a launch review

Agree on the metric pack before results exist, and keep it fixed. A one-page eval readout for a classifier, judge, or safety filter should contain:

  1. The question being answered and which error costs more, in one sentence each.
  2. n, the positive rate in the test set, and the positive rate expected in production.
  3. The confusion matrix at the chosen operating point, and how that point was chosen (on which split).
  4. The headline metric with a confidence interval, and the comparison to the baseline with a paired test.
  5. Per-class or per-slice results for anything rare that carries risk.
  6. For judge-scored results: judge version, judge-to-human kappa, and the human ceiling.
Principal asks
  • Was this metric chosen before or after seeing the results?
  • If the positive rate in production differs from the test set, what precision should we actually expect? (Recompute it from TPR and FPR.)
  • Which result would have made us not ship? If none, the evaluation was not a decision input.
Under the hoodTwo formulas that settle most arguments

Precision under prevalence shift. TPR and FPR are properties of the classifier; precision is not. If you validated at prevalence \(\pi\) and production runs at \(\pi'\):

\[ \mathrm{Precision}(\pi')=\frac{\mathrm{TPR}\,\pi'}{\mathrm{TPR}\,\pi'+\mathrm{FPR}\,(1-\pi')} \]A filter with TPR 0.90 and FPR 0.05 has precision 0.95 at \(\pi=0.5\), but only 0.15 at \(\pi'=0.01\).

The cost-optimal threshold. With calibrated scores, flag when the expected cost of not flagging exceeds the expected cost of flagging:

\[ p\,c_{FN} > (1-p)\,c_{FP}\iff p > \frac{c_{FP}}{c_{FP}+c_{FN}} \]If the scores are not calibrated, sweep thresholds on a validation split, pick the minimum-cost one, and report its cost on a separate test split.
def precision_at(tpr, fpr, prevalence):
    return tpr * prevalence / (tpr * prevalence + fpr * (1 - prevalence))

print(round(precision_at(0.90, 0.05, 0.50), 2))  # 0.95
print(round(precision_at(0.90, 0.05, 0.01), 2))  # 0.15
Eval lens
The most common failure is not the wrong metric. It is a metric whose definition, threshold, or test set quietly changed between the baseline and the candidate. Pin all three, and the choice of metric becomes much less contentious.
