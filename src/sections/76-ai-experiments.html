Designing experiments for AI systems: the whole guide in one design

Every earlier chapter supplies one piece of a trustworthy decision about an AI system: the statistics of Part I, the evaluation craft of Part II, the understanding of what training changed from Part IV, the judgment of Part V, and the design discipline of this part. This capstone puts them together. It covers offline evals treated as real experiments, online tests for model changes, interleaving, human evaluation, and pre-registration, then works one realistic launch from question to decision and ends with a single checklist that points each item back to the chapter that covers it.

1. Offline evals are experiments

Plain wordsSame exam, same day, same marker

To find out which of two students is better at maths, you give both the same exam, on the same day, marked by the same teacher. If one got an easier paper or a kinder marker, you would learn nothing. An offline eval is that exam for models: the same questions, the same settings, the same grader, so the only thing that differs is the model. And because models answer a little differently each time, you let each one sit the exam a few times.

For leadersTreat an eval run like a lab experiment
  • Fixed items: the eval set is frozen and versioned, and both models answer every item. Changing items between runs makes comparisons meaningless.
  • Paired comparison: compare per item, not just two averages. Pairing removes item difficulty from the noise and often cuts the required set size severalfold (statistics for eval sets).
  • Seeds and sampling settings recorded and repeated. A result that flips with the seed is not a result (leading eval work).
  • One change at a time, or a design that separates them. A run that changes the model, the prompt and the grader at once cannot say which one helped.
  • Clean items: checked for contamination against training data (contamination).
Under the hoodThe model behind a paired eval

Write the score of model \(m\) on item \(i\) with seed \(s\) as \(y_{mis} = \mu_m + b_i + \varepsilon_{mis}\): a model effect, an item difficulty shared by both models, and sampling noise. The paired difference \(d_i = \bar y_{Ai\cdot} - \bar y_{Bi\cdot}\) cancels \(b_i\), so

\[ \operatorname{Var}(\bar d) = \frac{1}{n}\left(\sigma^2_{\text{model}\times\text{item}} + \frac{2\sigma^2_\varepsilon}{S}\right) \]\(n\) items, \(S\) seeds per item and model. Item difficulty \(\sigma^2_b\) drops out entirely. More seeds shrink only the sampling term; only more items shrink the model-by-item term.

That decomposition tells you where to spend: if the seed term dominates, rerun; if the item term dominates, add items. Cluster the standard error by the unit that is actually independent (a conversation, a repository, a document) as in intervals, and run everything through a harness that records versions and seeds (building a harness).

2. Online A/B tests for model changes

Plain wordsA new chef on half the tables

Testing a new model on real users is like letting a new chef cook for half the tables while the old chef cooks for the rest. You keep each table with the same chef all evening, because switching mid-meal would confuse everyone. You watch whether diners are happier, but also whether the food comes out slower or costs more, because a better dish that takes an hour is not better.

For leadersWhat is different about testing models
  • Randomize by user, not by request. Users notice tone and capability, conversations carry memory, and per-request switching mixes the two models inside one conversation.
  • Cost and latency are first-class guardrails. A model change moves both, and they can matter more than quality for a free tier.
  • Safety is a guardrail with low base rates. Violations at 0.1% need very large samples to detect increases; pair the online guardrail with targeted offline red-team evals (safety).
  • Quality needs a measurement. Thumbs are sparse and biased. Most teams run an LLM judge on a sample of production traffic from both arms, validated against human labels (LLM as judge).
  • Expect novelty. A new model voice draws attention for a few days. Run at least two full weeks (A/B tests).
Under the hoodPitfalls specific to LLM traffic

Shared caches: a prompt or response cache shared across arms lets control serve treatment outputs; key caches by model version. Capacity: a treatment model on a smaller serving pool may queue under load, so latency differences partly reflect provisioning, which will change at 100%. Carryover: users who saw treatment and leave the test take learned behaviour (longer prompts, new tasks) with them, which matters for re-randomized follow-ups. Interference: shared workspaces or agents acting on shared resources violate independence; randomize at the workspace level. Triggering: if the change only affects some requests (say, those that call a tool), log a counterfactual trigger in control and analyse triggered users, with variance at the user level (choosing metrics).

3. Interleaving for ranking and search

Plain wordsTwo playlists shuffled into one

Two friends each suggest songs for a party. Instead of playing one friend's list on Friday and the other's on Saturday, you shuffle both lists together and see whose songs people skip less. Every guest hears both, on the same night, so the weather, the crowd and the mood are identical for both lists. Interleaving does this for search results: mix two rankers' results into one list and count whose results get clicked.

For leadersFast, sensitive, and narrow

Interleaving answers "which ranker do users prefer?" with far less traffic than an A/B test, because each user compares both rankers directly and between-user differences drop out. It suits retrieval for RAG, search, recommendations and tool selection. Its limit is scope: it measures preference within a results list, not downstream outcomes like task success, retention or cost. Use it to screen many ranking candidates quickly, then confirm the winner with an A/B test on the product metric.

Under the hoodTeam-draft interleaving

In team-draft interleaving (Radlinski, Kurup and Joachims, CIKM 2008), the two rankers act like captains picking teams: a coin decides who picks first in each round, each picks its highest-ranked result not already chosen, and every slot remembers which team placed it. Clicks credit the team that placed the clicked result; a query is a win for whichever ranker earned more clicks, and the test is whether wins exceed 50% over queries (a sign test, clustered by user). Chapelle, Joachims, Radlinski and Yue (TOIS 2012) validated interleaving at scale on two commercial search engines, comparing it with editorial judgments and studying its statistical efficiency. For generative systems, the analogue is a side-by-side preference shown to a sample of users, which inherits the position-bias issues covered next.

4. Human evaluation design

Plain wordsA blind taste test

In a fair taste test, tasters do not know which cola is which, the cups come in random order, and you first check that tasters agree with each other on a few practice cups. If they cannot tell the difference consistently, their verdict on the real test means little. Human evaluation of models needs the same three things: hide which model wrote what, randomize the order, and measure how often raters agree.

For leadersRatings are a measurement system to manage
  • Blinding: raters never see model names, and outputs are normalised for tell-tale formatting where possible.
  • Randomized order: left/right position randomized per item, because both people and judges prefer the first or second option at measurable rates.
  • Calibration: a rubric with worked examples, a calibration session, and gold items mixed in to catch drift and inattention.
  • Agreement: report inter-rater agreement on overlapping items. It is the ceiling on any judge or reward model trained on these labels (LLM as judge).
  • Rater effects: some raters are harsher. Assign items so each rater sees both models' outputs, and analyse with rater as a factor.

Public leaderboards built on blinded pairwise votes, such as Chatbot Arena (Chiang et al., 2024), show the design at scale, and also its limits: the voters and prompts are whoever shows up, which is a sampling question (who is in your sample?).

Under the hoodAgreement and the rater as a cluster

Cohen's kappa corrects raw agreement \(p_o\) for chance agreement \(p_e\):

\[ \kappa = \frac{p_o - p_e}{1 - p_e} \]For more than two raters or missing ratings, Krippendorff's alpha generalises the same idea.

Ratings from one rater are correlated, so a study with 2,000 ratings from 5 raters has far fewer than 2,000 independent observations for questions that involve rater variation. Fit a mixed model with item and rater random effects, or bootstrap over raters and items together. Plan the design so model and position are crossed with rater: every rater sees both models in both positions, which makes rater harshness and position bias estimable instead of confounded with the model effect.

5. Pre-registration and analysis plans

Plain wordsSealing your prediction in an envelope

A magician who writes a prediction, seals it in an envelope and hands it to the audience before the trick is convincing. One who announces the prediction after seeing the card is not. Pre-registration is the sealed envelope: write the plan for analysing the data before you see the data, and share it.

For leadersIt protects the team from itself

With dozens of metrics, segments and analysis choices, some combination will show a win by chance. Pre-registration, popularised in science partly in response to replication failures (Nosek et al., PNAS 2018, "The preregistration revolution"), makes the choices before the data can influence them. In product teams it is lightweight: the experiment brief plus an analysis plan, timestamped in the experiment system. Deviations are allowed and recorded; what is not allowed is presenting an exploratory finding as if it were the planned test.

Under the hoodWhat an analysis plan specifies
  1. Estimand: the population, the unit, the metric definition (code reference), and the contrast (difference, ratio, non-inferiority margin).
  2. Test and variance: e.g. difference in means with delta-method variance at the user level; CUPED covariate named.
  3. Error control: \(\alpha\), sidedness, correction across the primary and guardrails, and the look schedule with its spending function.
  4. Exclusions: bots, internal users, users with no exposure; decided by rules that cannot depend on arm.
  5. Segments: the few pre-planned ones, with interaction tests.
  6. Decision rule: what each outcome leads to, and what would change our mind.

Plain wordsProving "no worse", not "better"

This launch is not trying to make answers better. It is trying to save money without making them worse. That changes the question from "is it better?" to "is it close enough?" You set in advance how much worse is still acceptable (here, 1 point), and you ship only if the data rules out anything worse than that. "We did not see a difference" is not enough, because a small test never sees differences.

For leadersThe margin is a business decision

The 1-point margin is the number leadership must own: it says how much quality the company will trade for a 38% cost cut. Set it from the economics and user research before the test, not after seeing the estimate. A smaller margin needs quadratically more users: halving it to 0.5 points quadruples the sample. The decision rule also requires the cost saving to be real at test traffic levels, since the whole point of the launch is cost.

Under the hoodNon-inferiority sample size and decision
\[ H_0: \Delta \le -m \quad\text{vs}\quad H_1: \Delta > -m, \qquad n_{\text{per arm}} = \frac{(z_{1-\alpha} + z_{1-\beta})^2\; 2p(1-p)\,(1-\rho^2)}{m^2} \]Assumes the true difference is zero. \(m\) is the margin; \((1-\rho^2)\) is the variance kept by CUPED. Reject \(H_0\) (ship) when \(\hat\Delta - z_{1-\alpha}\,\mathrm{SE} > -m\).

With an observed difference of −0.3 points and standard error 0.35 points, the one-sided lower bound is \(-0.3 - 1.645 \times 0.35 = -0.88\), above −1, so the rule says ship.

import math
from statistics import NormalDist

Z = NormalDist().inv_cdf                     # standard normal quantile

def noninferiority_n(p, margin, alpha=0.05, power=0.8, variance_kept=1.0):
    """Users per arm to show the new model is at most `margin` worse (one-sided test).

    Assumes the true difference is zero. variance_kept below 1 models CUPED (1 - rho^2)."""
    z = Z(1 - alpha) + Z(power)
    return math.ceil(z * z * 2 * p * (1 - p) * variance_kept / margin ** 2)

def decide(diff, se, margin, alpha=0.05):
    """Ship only if the one-sided lower confidence bound sits above -margin."""
    lower = diff - Z(1 - alpha) * se
    return lower, lower > -margin

n = noninferiority_n(0.62, 0.01)                      # 62% weekly task success, 1-point margin
n_cuped = noninferiority_n(0.62, 0.01, variance_kept=0.6)
print(n, n_cuped)                                     # 29133 17480
days = math.ceil(n_cuped / 4_000)                     # 4,000 new eligible users per arm per day
print(days, 7 * math.ceil(days / 7))                  # 5 7  (round up to whole weeks)
lower, ship = decide(diff=-0.003, se=0.0035, margin=0.01)
print(f"{lower:.4f} {'ship' if ship else 'hold'}")    # -0.0088 ship
// Rust's standard library has no normal quantile, so we inline Acklam's rational
// approximation (relative error about 1e-9), which agrees with Python's NormalDist here.
fn z(p: f64) -> f64 {
    let a = [-3.969683028665376e1, 2.209460984245205e2, -2.759285104469687e2, 1.383577518672690e2, -3.066479806614716e1, 2.506628277459239];
    let b = [-5.447609879822406e1, 1.615858368580409e2, -1.556989798598866e2, 6.680131188771972e1, -1.328068155288572e1];
    let c = [-7.784894002430293e-3, -3.223964580411365e-1, -2.400758277161838, -2.549732539343734, 4.374664141464968, 2.938163982698783];
    let d = [7.784695709041462e-3, 3.224671290700398e-1, 2.445134137142996, 3.754408661907416];
    let tail = |q: f64| (((((c[0] * q + c[1]) * q + c[2]) * q + c[3]) * q + c[4]) * q + c[5]) / ((((d[0] * q + d[1]) * q + d[2]) * q + d[3]) * q + 1.0);
    if p < 0.02425 {
        tail((-2.0 * p.ln()).sqrt())
    } else if p > 1.0 - 0.02425 {
        -tail((-2.0 * (1.0 - p).ln()).sqrt())
    } else {
        let q = p - 0.5;
        let r = q * q;
        (((((a[0] * r + a[1]) * r + a[2]) * r + a[3]) * r + a[4]) * r + a[5]) * q / (((((b[0] * r + b[1]) * r + b[2]) * r + b[3]) * r + b[4]) * r + 1.0)
    }
}

/// Users per arm to show the new model is at most `margin` worse (one-sided test).
/// Assumes the true difference is zero. variance_kept below 1 models CUPED (1 - rho^2).
fn noninferiority_n(p: f64, margin: f64, alpha: f64, power: f64, variance_kept: f64) -> u64 {
    let zz = z(1.0 - alpha) + z(power);
    (zz * zz * 2.0 * p * (1.0 - p) * variance_kept / margin.powi(2)).ceil() as u64
}

/// Ship only if the one-sided lower confidence bound sits above -margin.
fn decide(diff: f64, se: f64, margin: f64, alpha: f64) -> (f64, bool) {
    let lower = diff - z(1.0 - alpha) * se;
    (lower, lower > -margin)
}

fn main() {
    let n = noninferiority_n(0.62, 0.01, 0.05, 0.8, 1.0); // 62% weekly task success, 1-point margin
    let n_cuped = noninferiority_n(0.62, 0.01, 0.05, 0.8, 0.6);
    println!("{} {}", n, n_cuped); // 29133 17480
    let days = (n_cuped as f64 / 4_000.0).ceil() as u64; // 4,000 new eligible users per arm per day
    println!("{} {}", days, 7 * ((days as f64) / 7.0).ceil() as u64); // 5 7  (round up to whole weeks)
    let (lower, ship) = decide(-0.003, 0.0035, 0.01, 0.05);
    println!("{:.4} {}", lower, if ship { "ship" } else { "hold" }); // -0.0088 ship
}

One question through the whole guide

The free-tier launch above, walked station by station. Numbers are illustrative.

Everything starts with a decision, not a curiosity. The team writes the question, the margin they will accept, and what they will do with each answer. Because v8 is meant to save money, the question is "no worse than 1 point", a non-inferiority test.

The team runs both models on 1,500 frozen items drawn from production, three seeds each, and compares item by item. v8 is 0.6 points behind, but the interval reaches −1.7, past the margin. Offline evidence narrows the question; it cannot answer it here.

Task success online will be graded by an LLM judge, so the judge is checked first. On 600 items labelled by two people, the judge agrees with humans almost as often as humans agree with each other, with position bias controlled by swapping order.

Knowing how v8 was made predicts where it might break. Distillation tends to lose rare skills first, so the team adds a guardrail on task success in the five smallest languages, alongside safety and refusal rates. The training chapters turn into a list of things to measure.

Free-tier users are split by a hash of their ID for two full weeks, with exposure logged when the first answer renders and a trace ID on every event. Before anyone looks at task success, the split passes the SRM check and exposure is equal in both arms.

At day 14 the primary metric is read once. The lower bound sits above the margin, cost and latency fall, no guardrail breaks, and the effect is steady across exposure cohorts. The rule written on day 0 says ship, with a holdout to watch the long run. Part V's reviewer questions have answers on file.

Eval lens
The deepest lesson of the guide is that every number about a model is the output of an experiment, whether or not anyone designed it as one. A benchmark score has a sample (the items), a measurement (the grader), a comparison (the baseline), and noise (seeds, items, raters). An online metric adds assignment and exposure. Asking the design questions of every number, offline or online, is what separates an eval program from a leaderboard.
Principal asks
What decision does this experiment inform, and what result would change it? Is this a superiority or a non-inferiority question, and who set the margin? What did the offline eval establish, with what interval, and why is that not enough? What did training change that we should guard against? Who is sampled, how are they assigned, and is the analysis at the same unit? Which numbers are pre-registered, and what is exploratory? When will we look, and what stops the test early? If the result surprises us, which logs will explain it?
Common mistakes
Testing a cost-saving model for superiority and calling a flat result "no worse". Shipping on an offline win without an online test, or running an online test without offline screening. Randomizing model changes per request. Using an unvalidated judge as the primary metric. Unblinded human evals with fixed left/right order. Changing the analysis after seeing the data without saying so. Forgetting that the guardrails need power too.
