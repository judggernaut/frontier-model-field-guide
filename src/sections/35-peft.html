LoRA and parameter-efficient tuning

Full fine-tuning updates every weight in the model. Parameter-efficient fine-tuning (PEFT) freezes the pretrained weights and trains a small add-on instead. LoRA is by far the most used method. It makes customisation cheap enough to run on one GPU, and lets one server hold thousands of variants of the same base model.

Why not just fine-tune everything?

Plain wordsSticky notes instead of rewriting the book

Full fine-tuning is like reprinting a 1,000-page encyclopedia every time you want to change how it reads. LoRA leaves the book alone and adds a thin stack of sticky notes that adjust it. The notes are tiny, you can swap them in and out, and you can keep a different stack for each customer. When you want a final copy, you can even print the notes into the pages.

For leadersThe cost picture

Full fine-tuning with the Adam optimiser in mixed precision needs about 16 bytes of GPU memory per parameter before activations: the weights, their gradients, a full-precision master copy, and two optimiser statistics. That is roughly 128 GB for an 8B model and over 1 TB for a 70B model, so full fine-tuning means a multi-GPU cluster. LoRA trains well under 1% of the parameters, so the optimiser and gradient memory nearly vanish and the frozen base dominates. QLoRA goes further and stores the frozen base in 4 bits.

Cheaper training

Fits on far fewer GPUs. The original LoRA paper reports about 3× less GPU memory and 10,000× fewer trainable parameters than full fine-tuning GPT-3 175B (Hu et al., 2021).

Cheap storage

An adapter is megabytes to a few gigabytes, not a full copy of the model.

Cheap serving

Many adapters share one base model in memory. Systems such as S-LoRA (Sheng et al., 2023) and Punica (Chen et al., 2023) batch requests for different adapters together.

Less forgetting

Because LoRA changes few directions, it tends to damage general ability less, at the price of learning less from large datasets.

How LoRA works

Plain wordsA big change described by a few knobs

A weight matrix in a model might have 16 million numbers. LoRA bets that the change you need during fine-tuning is simple, so it can be described with far fewer numbers: two thin matrices that multiply together to make a full-size correction. The thinness is called the rank. Rank 8 means the whole correction is built from 8 basic patterns.

Under the hoodThe low-rank update

For a frozen weight \(W_0 \in \mathbb{R}^{d \times k}\), LoRA learns \(B \in \mathbb{R}^{d \times r}\) and \(A \in \mathbb{R}^{r \times k}\) with \(r \ll \min(d,k)\):

\[ h = W_0 x + \frac{\alpha}{r}\, B A x \]\(A\) starts random (Gaussian), \(B\) starts at zero, so \(BA = 0\) and training begins exactly at the pretrained model. \(\alpha\) is a fixed scale; dividing by \(r\) keeps the update size roughly stable when you change the rank.

The update has \(r(d+k)\) trainable parameters instead of \(dk\). For a 4096 × 4096 projection at rank 16, that is 131,072 instead of 16.8 million, under 1%. After training, \(W = W_0 + \frac{\alpha}{r}BA\) can be merged into the base weights, so a single-adapter deployment has no extra inference cost.

import torch, torch.nn as nn

class LoRALinear(nn.Module):
    def __init__(self, base: nn.Linear, r=16, alpha=32):
        super().__init__()
        self.base = base
        for p in self.base.parameters():
            p.requires_grad = False                     # the pretrained weight stays frozen
        d_out, d_in = base.weight.shape
        self.A = nn.Parameter(torch.randn(r, d_in) / r**0.5)
        self.B = nn.Parameter(torch.zeros(d_out, r))    # zero init: BA = 0 at step 0
        self.scale = alpha / r

    def forward(self, x):
        return self.base(x) + self.scale * (x @ self.A.T @ self.B.T)

    @torch.no_grad()
    def merge(self):
        # fold the adapter into the weight for zero-overhead serving
        self.base.weight += self.scale * self.B @ self.A

layer = LoRALinear(nn.Linear(4096, 4096, bias=False), r=16)
trainable = sum(p.numel() for p in layer.parameters() if p.requires_grad)
print(trainable, f"{trainable / 4096**2:.2%}")  # 131072 0.78%

Practical defaults have shifted since 2021. The original paper adapted only the attention query and value projections. Later work, including QLoRA and the Thinking Machines "LoRA Without Regret" study (2025), found that adapting all linear layers, especially the MLP blocks, matters more than raising the rank. The same study reports that the best LoRA learning rate is about 10× the best full fine-tuning rate. Rank-stabilised LoRA (Kalajdzievski, 2023) scales by \(\alpha/\sqrt{r}\) instead of \(\alpha/r\) so that high ranks keep learning.

Why a low-rank update is enough

Plain wordsMost changes are simple

A random scribble needs every pixel to describe it. A photo of the sky is mostly a smooth gradient and can be described by a few numbers. Fine-tuning changes turn out to look more like the sky than the scribble. That's why a few patterns capture most of the change.

Under the hoodIntrinsic dimension and the Eckart–Young theorem

The best rank-\(r\) approximation of a matrix in Frobenius norm keeps its top \(r\) singular values (Eckart–Young). The fraction of squared norm kept is

\[ \frac{\lVert M_r \rVert_F^2}{\lVert M \rVert_F^2} = \frac{\sum_{i=1}^{r}\sigma_i^2}{\sum_{i}\sigma_i^2} \]

Aghajanyan et al. (2021) showed that fine-tuning a pretrained language model can reach most of its full performance while optimising in a random subspace of only hundreds to thousands of dimensions, and that larger, better-pretrained models have lower intrinsic dimension. LoRA exploits the same fact per weight matrix. The caveat from Biderman et al. (2024, "LoRA Learns Less and Forgets Less"): on large-scale code and math training, full fine-tuning learns perturbations with rank 10 to 100× higher than typical LoRA settings, and LoRA falls behind. Low rank is a good bet for adapting behaviour, not for teaching large amounts of new knowledge.

Watch out
Merging a LoRA adapter into a quantised base is not exact: you must dequantise, add, and requantise, which changes outputs slightly. Evaluate the artefact you actually serve, not the training-time model with adapter attached.
Under the hoodWhat QLoRA adds
  • NF4 (4-bit NormalFloat). Pretrained weights are roughly normally distributed, so NF4 places its 16 levels at quantiles of a normal distribution. Each block of 64 weights has its own scale.
  • Double quantisation. The per-block scales are themselves quantised, saving about 0.37 bits per parameter.
  • Paged optimisers. Optimiser state can spill to CPU memory during spikes instead of crashing with out-of-memory errors.

Gradients flow through the dequantised 4-bit weights into the bf16 LoRA parameters; the base itself never updates.

LoRA beyond SFT

For leadersRL, multi-tenant serving, and when to say no

RL. The Thinking Machines study (2025) found LoRA matches full fine-tuning for reinforcement learning even at very low rank, including rank 1. The intuition: a policy-gradient episode carries only a few bits of information (did it succeed?), so the total information learned is small enough to fit in a tiny adapter. That makes LoRA attractive for RL with verifiable rewards, where many runs and ablations are needed.

Multi-tenant products. Per-customer or per-task adapters on a shared base are the standard way to offer fine-tuning as a product. The eval burden scales with the number of adapters: each one needs a regression check against the base.

When to say no. If the goal is a new capability that the base model can't do at all, or the dataset is in the billions of tokens, LoRA is likely to underperform. Expect to need full fine-tuning or continued pretraining.

Eval lens

A LoRA result needs three comparisons, not one: the adapter versus the base on the target task (did it learn?), the adapter versus the base on a general regression suite (did it forget?), and the merged or quantised serving artefact versus the training-time model (did deployment change it?). Ranks and learning rates interact, so compare tuned configurations, not one LoRA setting against a tuned full fine-tune.

Principal asks
  • Which modules did we adapt, at what rank, and did we tune the learning rate separately for LoRA?
  • Is the gap to full fine-tuning on the target metric outside the noise, and what is the gap on the forgetting suite?
  • Are we evaluating the merged, quantised artefact that ships?
  • How many adapters will we serve, and who owns their regression testing?
