Diagnosing a regression: model, harness, data, or infrastructure?

An eval suite comes back with an anomalous number a few hours before a decision. The job is to say, quickly and with evidence, whether anything is actually wrong, and if so whether it is the model, the harness, the data, or the infrastructure. This chapter gives an order of operations that answers the cheapest questions first.

Plain wordsThe thermometer before the doctor

If a child's temperature reading looks high, a sensible parent first checks the thermometer. Is it working? Did they measure right after a hot bath? Only then do they worry about illness.

A falling eval score is the same. Before blaming the model, check whether the drop is bigger than normal noise, whether the measuring setup changed, and whether the computers running the test had problems. Most "regressions" turn out to be the thermometer.

For leadersIncident response for a number

Treat an eval regression like a production incident: one owner, a fixed checklist, a written timeline, and a clear exit. The first question is not "what broke" but "did anything break". Asking it first protects the team's time and stops a launch being blocked by noise, or approved past a real problem.

A useful operating rule: the triage owner reports within a fixed window (a few hours) with one of four verdicts, each with its evidence.

Noise

The change is inside the confidence interval. No action; note it and move on.

Measurement

Harness, judge, prompt, or task set changed. Fix the measurement and rerun before anyone discusses the model.

Infrastructure

Timeouts, rate limits, or errors spiked. Rerun under healthy conditions.

Model

Reproduces on replay and is concentrated in specific capabilities. Escalate with example outputs and the affected slices.

What goes in the launch review afterwards: the verdict, the interval, the slice breakdown, twenty example outputs that show the failure, and what changes in the harness or checks so this class of problem is caught automatically next time.

Principal asks
  • Is this outside the noise band? What is the interval on the delta, computed paired?
  • Is the drop uniform or concentrated? Which slice contributes most of the total?
  • What changed besides the model? Show me the config diff.
  • Did the previous model also drop when rerun on today's harness?
  • Have you read the failing outputs yourself?

The order to check things in

  1. Is it real? Compute the interval before you investigate. Use the paired comparison from eval statistics: the same tasks, both models, discordant pairs. A 3 point drop inside the noise band is not an incident. This step alone saves days and is the one people skip.
  2. Is it everywhere or somewhere? Break the delta down by task category, language, input length, source. A uniform drop points at the model or the harness. A drop concentrated in one slice points at data or a specific capability.
  3. Did anything non-model change? Harness version, judge model or prompt, timeout, concurrency, temperature, task set membership, dependency versions. Diff the config before you diff the model.
  4. Error and retry rates. A drop that arrives with a spike in timeouts is infrastructure wearing a model costume. See the harness chapter for why errors and retries bias scores.
  5. Replay. Rerun a sample of the regressed tasks against the previous model with today's harness. If the old model also drops, it is not the model.
  6. Read the outputs. Twenty of them, by hand, every time. The failure mode is usually visible and usually not what the metric suggested.
Under the hoodSlice by contribution, not by percentage change

The total change in mean score decomposes exactly into slice contributions. With \(N\) tasks split into slices \(s\) of size \(n_s\) and per-slice mean change \(\bar d_s\):

\[ \Delta_{\text{total}} = \frac{1}{N}\sum_{s} n_s\,\bar d_s \]Each slice's contribution is \(n_s \bar d_s / N\). Rank slices by this, not by \(\bar d_s\) alone, or a tiny slice with a big swing will send you down the wrong path. This identity holds when slices partition the tasks.
def slice_deltas(before: dict[str, float], after: dict[str, float],
                 slices: dict[str, list[str]]) -> list[tuple[str, float, int]]:
    """Where did the drop actually happen. Sort by contribution to the total
    delta, not by percentage change, or a tiny slice with a big swing will
    send you down the wrong path."""
    out = []
    for name, task_ids in slices.items():
        ids = [t for t in task_ids if t in before and t in after]
        if not ids:
            continue
        d = sum(after[t] - before[t] for t in ids) / len(ids)
        contribution = d * len(ids)
        out.append((name, d, len(ids), contribution))
    out.sort(key=lambda x: x[3])            # most negative contribution first
    return [(n, round(d, 4), k) for n, d, k, _ in out]
Watch out
Slicing is a multiple comparison. With twenty slices, one will look significant by chance at the 5% level. Treat the slice view as a way to decide where to read outputs, not as a finding in itself, or apply a correction such as Benjamini–Hochberg (see multiple comparisons).

Replay as a two-by-two

The replay step is cleanest as a small factorial: old and new model crossed with old and new harness. If the drop appears only in the new-harness column, the harness is the cause. If it appears only in the new-model row, it is the model. If it appears in only one cell, look for an interaction, such as a new prompt template that only the new model handles badly.

Eval lens
Every triage should end with a change to the harness or the automated checks, so the same class of false alarm or real regression is caught without a human next time. A regression you diagnosed twice is a missing test.
