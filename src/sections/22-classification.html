Classification metrics, from precision to AUC

Every LLM judge is a classifier. So is a safety filter, a regression detector, an intent labeller, and an auto-approve gate. This chapter starts with someone sorting mail and ends with the metrics you would put in a launch review. One spam example runs through every chart, so each idea builds on the last.

The four outcomes

Plain wordsA helper sorts your mail into two piles

Your helper looks at every letter and decides: junk pile or keep pile. Each time, they can be right in two ways and wrong in two ways.

True positive

It was junk, and they put it in the junk pile. Good catch.

False positive

It was a real letter, and they threw it in the junk pile. A false alarm.

False negative

It was junk, and they left it in the keep pile. It slipped through.

True negative

It was a real letter, and they kept it. Also good.

Every metric in this chapter is a different way of counting those four piles. Each one asks a simple question:

  • PrecisionWhen the helper says "junk," how often are they right?
  • RecallOf all the junk that arrived, how much did they find?
  • AccuracyOut of every letter, how many did they sort correctly?
  • F1One score that is only high when precision and recall are both high.

"Positive" means the thing you are hunting for. Here that is spam. It does not mean good.

A spam model does not really say "spam" or "not spam." It gives each email a score from 0 to 1 for how spammy it looks. You choose a cutoff, and anything at or above it goes to the spam folder. That cutoff is the threshold. Think of it as the passing grade on a test: the scores are fixed, but you decide where the line goes.

Confusion matrix

The 2×2 grid is the confusion matrix. Rows are the truth, columns are what the model decided. Everything else in this chapter is built from those four numbers.

For leadersA metric without its confusion matrix is unauditable

When someone shows you "precision 0.92," three things are hidden: the threshold, the prevalence of the positive class in the test set, and how many examples sat behind the number. Each one can move the headline more than the model change being reported. Make it a standing rule that any classifier metric in a review comes with the confusion matrix, the threshold, and n.

The second rule: decide which mistake costs more before you look at results. A false positive in a safety filter blocks a legitimate user. A false negative lets a harmful output through. A false positive in a regression detector costs an engineer an afternoon; a false negative ships a regression. If the team cannot say which error is worse, no metric choice will be defensible.

Principal asks
  • At what threshold, and who chose it? Was it tuned on the same data you are reporting?
  • What is the positive rate in this test set, and what is it in production?
  • Which error are we optimising against, and what does one of each cost?
Under the hoodThe confusion matrix is a function of the threshold

Given scores \(s_i\), labels \(y_i \in \{0,1\}\), and a threshold \(\tau\), the prediction is \(\hat y_i = \mathbb{1}[s_i \ge \tau]\). Each cell counts a combination:

\[ \mathrm{TP}(\tau)=\sum_i \mathbb{1}[\hat y_i=1, y_i=1],\quad \mathrm{FP}(\tau)=\sum_i \mathbb{1}[\hat y_i=1, y_i=0],\quad \mathrm{FN}(\tau)=\sum_i \mathbb{1}[\hat y_i=0, y_i=1] \]TN is everything else. Raising \(\tau\) can only move items from the predicted-positive column to the predicted-negative column, so TP and FP never increase as \(\tau\) rises.

Report a single precision or recall and you have silently reported a threshold choice as if it were a property of the model. Two teams can report very different F1 for the same model because they picked different operating points. Threshold-free metrics (section on AUC below) sidestep this and bring their own problems.

def confusion(y_true, y_pred):
    """The four numbers everything else is built from.
    Always compute this first and show it next to any derived metric."""
    tp = sum(1 for a, b in zip(y_true, y_pred) if a == 1 and b == 1)
    fp = sum(1 for a, b in zip(y_true, y_pred) if a == 0 and b == 1)
    fn = sum(1 for a, b in zip(y_true, y_pred) if a == 1 and b == 0)
    tn = sum(1 for a, b in zip(y_true, y_pred) if a == 0 and b == 0)
    return {"tp": tp, "fp": fp, "fn": fn, "tn": tn}

Nobody needs to act in bad faith for this to happen. A team that iterates on a metric for months will drift toward whatever the metric rewards. The defence is a metric pack fixed in advance, not a single number.

Under the hoodF-beta, and the demonstration that F1 ignores TN
\[ F_\beta = (1+\beta^2)\,\frac{P\cdot R}{\beta^2 P + R} \]\(\beta>1\) weights recall more, \(\beta<1\) weights precision more. \(F_1\) is the harmonic mean of \(P\) and \(R\), which punishes imbalance: \(P=0.9, R=0.1\) gives 0.18, not 0.5.
def f_beta(precision, recall, beta=1.0):
    """beta > 1 weights recall more, beta < 1 weights precision more.
    beta = 2 says a miss costs about four times a false alarm (beta squared)."""
    if precision + recall == 0:
        return 0.0
    b2 = beta * beta
    return (1 + b2) * precision * recall / (b2 * precision + recall)
Watch out
Two classifiers, both with TP = 80, FP = 20, FN = 20. Scenario A has TN = 80; scenario B has TN = 9,980. Both score F1 = 0.800. MCC separates them: 0.600 versus 0.798. Same F1, materially different classifiers, because F1 never looks at the TN cell.

Plain wordsSame four boxes, reassigned

Legit precision asks, "of what reached my inbox, how much was really legit?" That is TN out of TN + FN. Legit recall asks, "of all real emails, how many reached my inbox?" That is TN out of TN + FP. Legit recall has its own name, specificity, common in medical testing. Accuracy is the odd one out: it is one number for the whole model.

  • Macro average is a plain average of each class's score. Every class counts equally, so a rare class you care about cannot hide.
  • Weighted average weights each class by how many examples it has. The big class has more say.
  • Micro average pools all the counts first, then computes. For one-label-per-item problems it equals accuracy.

For leadersPer class first, averages second

Ask for the per-class table before any average. The averaging choice is a statement about what matters: macro says every class matters equally, weighted says the traffic mix matters, micro says only total volume matters. For anything where rare cases carry the risk (safety categories, unusual intents, rare failure modes), weighted and micro hide exactly what you need to see.

The actionable unit is usually a confusable pair, not a score. "Macro F1 0.81" tells you nothing to do. "Refactor and rename are confused 40% of the time" tells you to fix the taxonomy or the labelling guide.

Under the hoodThe three averages, precisely
\[ F_1^{\text{macro}}=\frac1K\sum_{k=1}^K F_1^{(k)},\qquad F_1^{\text{weighted}}=\sum_{k=1}^K \frac{n_k}{n}F_1^{(k)},\qquad F_1^{\text{micro}}=\frac{2\sum_k \mathrm{TP}_k}{2\sum_k \mathrm{TP}_k+\sum_k \mathrm{FP}_k+\sum_k \mathrm{FN}_k} \]In single-label multiclass, every false positive for one class is a false negative for another, so \(\sum_k \mathrm{FP}_k=\sum_k \mathrm{FN}_k\) and micro-F1 equals accuracy.
from collections import Counter

def multiclass_report(y_true, y_pred):
    """Per-class metrics plus all three averages. When macro and weighted
    diverge sharply, that gap is the finding."""
    labels = sorted(set(y_true) | set(y_pred))
    per = {}
    for lab in labels:
        tp = sum(a == lab and b == lab for a, b in zip(y_true, y_pred))
        fp = sum(a != lab and b == lab for a, b in zip(y_true, y_pred))
        fn = sum(a == lab and b != lab for a, b in zip(y_true, y_pred))
        p = tp / (tp + fp) if tp + fp else 0.0
        r = tp / (tp + fn) if tp + fn else 0.0
        per[lab] = {"f1": 2 * p * r / (p + r) if p + r else 0.0,
                    "support": tp + fn, "tp": tp, "fp": fp, "fn": fn}
    n = len(y_true)
    macro = sum(v["f1"] for v in per.values()) / len(labels)
    weighted = sum(v["f1"] * v["support"] for v in per.values()) / n
    micro = sum(a == b for a, b in zip(y_true, y_pred)) / n
    confused = Counter((a, b) for a, b in zip(y_true, y_pred) if a != b).most_common(3)
    return {"per_class": per, "macro_f1": macro, "weighted_f1": weighted,
            "micro_f1": micro, "top_confused_pairs": confused}

Plain wordsYou can only choose which mistakes to make

With a weak model, the humps overlap. Wherever you put the threshold, it cuts through both, so you only get to choose which mistakes to make. Raise model quality and the humps pull apart. Then one threshold can catch most spam while flagging almost no legit mail.

Key idea
This is the precision-recall trade-off. The only way to improve precision and recall together is to separate the humps, which means a better model, not a better threshold.
For leadersThreshold work versus model work

When a team reports that precision went up, ask whether recall went down. If it did, the threshold moved and the model did not get better. That can still be the right call, but it is a product decision about error costs, not a research result. Real improvement shows up as a higher curve (a higher AUC), or as both precision and recall improving at a fixed threshold. Budget accordingly: threshold tuning is cheap and fast; separating the humps takes better features, better data on the hard cases, or a stronger model.

Building an ROC curve

An ROC curve shows what happens at every threshold at once. Each threshold gives one dot. The dot goes up for spam caught and right for good emails wrongly flagged. Up is good. Right is bad.

A great model climbs straight up before it moves right, hugging the top-left corner. A useless model moves up and right at the same pace along the diagonal: coin flipping. ROC stands for "receiver operating characteristic," a name left over from radar engineering. Read it as the "caught versus wrongly flagged" chart.

AUC: one number for the whole curve

AUC means area under the curve: how much of the box the curve fills. A perfect model scores 1.0. Random guessing scores 0.5. Because it covers every threshold, AUC ignores the threshold you picked and measures how far apart the humps are.

Key idea
Plain-English meaning of ROC-AUC: pick one random spam email and one random legit email. AUC is the chance the model gives the spam the higher score. In the ten-email example, spam outscores legit in 22 of 25 pairs, and 22 ÷ 25 = 0.88.

Plain wordsWhy there is a second curve

Drag spam share down to 5%. ROC-AUC does not change, because ROC never looks at how common each class is. The PR curve sinks, because even a small false alarm rate on a huge pile of legit email produces lots of false positives. ROC-AUC can look excellent while precision is poor. When the thing you are hunting for is rare, PR-AUC is the more honest number. Its random-guessing line sits at the spam share, so a PR-AUC of 0.3 is great when spam is 5% and poor when it is 50%.

Rough guide for ROC-AUC: 0.5 random, 0.7 weak, 0.8 decent, 0.9 and up strong. What counts as good depends on the problem.

For leadersAUC chooses the model; the confusion matrix makes the ship decision

Use AUC to compare models or versions, because it does not depend on a threshold someone picked. Then make the ship decision on the confusion matrix at the operating point you will actually run. A model with higher AUC can be worse at your operating point if its curve crosses the other one there.

Watch out
Same classifier, same data, 2% prevalence, in a simulation of 5,000 samples: ROC-AUC 0.928, PR-AUC 0.470, against a PR-AUC baseline of 0.020. ROC-AUC says excellent. PR-AUC says mediocre but far better than chance. For rare-positive problems (safety violations, cheating detection, rare regressions) the PR number is the one telling the truth.
Principal asks
  • Is this ROC-AUC or PR-AUC, and what is the positive rate?
  • Do the two models' curves cross? Where is our operating point relative to the crossing?
  • Does the score come with confidence intervals? (AUC on 200 examples has a wide one; see intervals and the bootstrap.)
Under the hoodAUC as a rank statistic, and average precision

ROC-AUC equals the probability that a random positive outscores a random negative, which is the Mann–Whitney U statistic scaled to [0, 1]:

\[ \mathrm{AUC}=P(S^+ > S^-) + \tfrac12 P(S^+=S^-) = \frac{R_+ - n_+(n_+ + 1)/2}{n_+\,n_-} \]\(R_+\) is the sum of the ranks of the positive examples when all scores are ranked together (ties get average ranks); \(n_+\) and \(n_-\) are the class counts.

PR-AUC is usually computed as average precision: walk down the ranking and average the precision at each point where a positive appears.

\[ \mathrm{AP}=\frac{1}{n_+}\sum_{k:\,y_{(k)}=1} \mathrm{Precision}@k \]The baseline for a random ranking is the prevalence \(\pi = n_+/n\), which is why PR-AUC must always be read next to \(\pi\).

Precision depends on prevalence directly. If a classifier has true positive rate \(\mathrm{TPR}\) and false positive rate \(\mathrm{FPR}\), its precision at prevalence \(\pi\) is

\[ \mathrm{Precision}(\pi)=\frac{\mathrm{TPR}\cdot\pi}{\mathrm{TPR}\cdot\pi+\mathrm{FPR}\cdot(1-\pi)} \]TPR and FPR (the ROC axes) do not change with \(\pi\); precision does. That single line explains why ROC is prevalence-blind and PR is not.
def roc_auc(y_true, scores):
    """Probability a random positive outscores a random negative (ties count half)."""
    order = sorted(range(len(scores)), key=lambda i: scores[i])
    ranks = [0.0] * len(scores)
    i = 0
    while i < len(order):
        j = i
        while j + 1 < len(order) and scores[order[j + 1]] == scores[order[i]]:
            j += 1
        avg = (i + j) / 2 + 1            # tied items share the average rank
        for k in range(i, j + 1):
            ranks[order[k]] = avg
        i = j + 1
    n_pos = sum(y_true)
    n_neg = len(y_true) - n_pos
    r_pos = sum(r for r, y in zip(ranks, y_true) if y == 1)
    return (r_pos - n_pos * (n_pos + 1) / 2) / (n_pos * n_neg)


def average_precision(y_true, scores):
    """Step-wise PR-AUC: mean precision at each rank where a positive appears."""
    order = sorted(range(len(scores)), key=lambda i: -scores[i])
    tp, ap = 0, 0.0
    for rank, i in enumerate(order, start=1):
        if y_true[i] == 1:
            tp += 1
            ap += tp / rank
    return ap / sum(y_true)

Better single numbers: MCC, balanced accuracy, kappa

If you must report one number, these are better choices than F1. Each still has a catch.

For leadersWhich single number for which audience
NumberReads asBest forCatch

MCCCorrelation between prediction and truth, −1 to +1Comparing models with one numberUnintuitive scale; undefined when the model predicts one class

Under the hoodDefinitions
\[ \mathrm{MCC}=\frac{\mathrm{TP}\cdot\mathrm{TN}-\mathrm{FP}\cdot\mathrm{FN}}{\sqrt{(\mathrm{TP}+\mathrm{FP})(\mathrm{TP}+\mathrm{FN})(\mathrm{TN}+\mathrm{FP})(\mathrm{TN}+\mathrm{FN})}},\qquad \mathrm{BA}=\tfrac12\Big(\tfrac{\mathrm{TP}}{\mathrm{TP}+\mathrm{FN}}+\tfrac{\mathrm{TN}}{\mathrm{TN}+\mathrm{FP}}\Big) \]MCC uses all four margins, so swapping the class labels leaves it unchanged. F1 does not have that property.
\[ \kappa=\frac{p_o-p_e}{1-p_e},\qquad p_e=\frac{(\mathrm{TP}+\mathrm{FP})(\mathrm{TP}+\mathrm{FN})+(\mathrm{TN}+\mathrm{FN})(\mathrm{TN}+\mathrm{FP})}{n^2} \]\(p_o\) is observed agreement (plain accuracy); \(p_e\) is the agreement two independent raters with the same marginals would reach by luck. On a 95/5 split, luck alone gives about 90%.
import math

def mcc(tp, fp, fn, tn):
    den = math.sqrt((tp + fp) * (tp + fn) * (tn + fp) * (tn + fn))
    return (tp * tn - fp * fn) / den if den else 0.0   # 0 = chance when undefined

def balanced_accuracy(tp, fp, fn, tn):
    return (tp / (tp + fn) + tn / (tn + fp)) / 2

def kappa(tp, fp, fn, tn):
    n = tp + fp + fn + tn
    po = (tp + tn) / n
    pe = ((tp + fp) * (tp + fn) + (tn + fn) * (tn + fp)) / (n * n)
    return (po - pe) / (1 - pe) if pe != 1 else 0.0

# The "flag nothing" model on 1% positives: accuracy 0.99, MCC 0, BA 0.5, kappa 0
print(mcc(0, 0, 10, 990), balanced_accuracy(0, 0, 10, 990), kappa(0, 0, 10, 990))

MCC and kappa are often nearly identical on binary problems. Prefer MCC when scoring a model and kappa when scoring agreement between raters, because that is what each was designed to communicate.

Calibration: is the confidence honest?

Plain wordsA weather forecaster who says 70%

If a forecaster says "70% chance of rain" on 100 days, it should rain on about 70 of them. That is calibration. A model can rank emails perfectly (every spam above every legit) and still be badly wrong about how sure it should be. Ranking and honesty about confidence are different skills.

Calibration
Sharpening pushes confidence toward 0 and 1 without changing the ranking at all. Accuracy and AUC do not move. Watch ECE and Brier come apart. If you route, abstain or auto approve on a confidence score, this is the property that matters.
For leadersWhen calibration is the whole ballgame

Calibration matters whenever a downstream decision uses the confidence number itself: routing to a bigger model, abstaining and asking a human, auto-approving an action, or combining scores from several judges. Accuracy and AUC are blind to it. If a system makes decisions on confidence, require a reliability diagram and ECE in the review. The usual fix, temperature scaling on a held-out set, is cheap and does not change rankings, so there is rarely an excuse to ship miscalibrated scores.

Under the hoodBrier score and expected calibration error
\[ \mathrm{Brier}=\frac1n\sum_{i=1}^n (p_i-y_i)^2,\qquad \mathrm{ECE}=\sum_{b=1}^{B}\frac{|S_b|}{n}\,\big|\mathrm{acc}(S_b)-\mathrm{conf}(S_b)\big| \]Brier is a proper scoring rule: it is minimised by reporting your true belief. ECE buckets predictions by confidence \(S_b\) and compares mean confidence to observed accuracy in each bucket. ECE depends on the number of bins, so always state \(B\).
def brier(y_true, probs):
    # squared, not absolute: squaring is what makes it a proper scoring rule
    return sum((p - y) ** 2 for p, y in zip(probs, y_true)) / len(y_true)

def ece(y_true, probs, bins=10):
    n, total = len(y_true), 0.0
    for b in range(bins):
        lo, hi = b / bins, (b + 1) / bins
        idx = [i for i, p in enumerate(probs) if (lo < p <= hi) or (b == 0 and p == 0)]
        if not idx:
            continue
        conf = sum(probs[i] for i in idx) / len(idx)
        acc = sum(y_true[i] for i in idx) / len(idx)
        total += len(idx) / n * abs(acc - conf)
    return total
Note
In a simulation with 20% label noise, a moderately confident model scored Brier 0.162 and ECE 0.050. The same model pushed to 0.99 / 0.01 confidence scored Brier 0.196 and ECE 0.190: identical ranking, identical accuracy, nearly four times worse calibration.

Selective prediction: when the system can abstain

Instead of one accuracy number you get a curve: error as a function of how often the system is willing to answer. This is the right frame for any judge that can say "unsure," any agent that can ask the user before acting, and any classifier that can hand cases to a human.

Under the hoodThe coverage–risk curve

Sort by confidence \(c_i\) descending and answer only the top fraction \(\kappa\) (coverage). Risk is the error rate over the answered set only; abstained items are handed off, not counted wrong.

\[ \mathrm{risk}(\kappa)=\frac{1}{\lfloor\kappa n\rfloor}\sum_{i\in \text{top }\lfloor\kappa n\rfloor}\mathbb{1}[\hat y_i\neq y_i],\qquad \text{total cost}(\kappa)=\kappa\,\mathrm{risk}(\kappa)\,c_{\text{error}}+(1-\kappa)\,c_{\text{ask}} \]The area under the risk–coverage curve (AURC) summarises how well confidence tracks correctness; lower is better.
def coverage_risk(y_true, preds, conf, coverages=(1.0, 0.9, 0.8, 0.6, 0.5)):
    order = sorted(range(len(y_true)), key=lambda i: -conf[i])
    out = []
    for cov in coverages:
        k = max(1, int(cov * len(order)))
        err = sum(preds[i] != y_true[i] for i in order[:k]) / k
        out.append({"coverage": cov, "risk": err, "answered": k})
    return out

Expected cost: the metric that is actually about your problem

Everything above is a proxy. If you know the relative costs of the two errors, skip the proxies and minimise expected cost directly.

For leadersGet the cost ratio on the table

Most metric arguments are cost arguments in disguise. One team wants precision, another wants recall, and neither has said what a false alarm and a miss each cost. Force that number out, even as a rough ratio ("a missed harmful output is about 20 times worse than a wrongly blocked request"). Once it exists, the threshold choice is arithmetic and the argument ends.

Under the hoodCost per decision and the Bayes-optimal threshold
\[ \mathrm{Cost}(\tau)=\frac{c_{FP}\,\mathrm{FP}(\tau)+c_{FN}\,\mathrm{FN}(\tau)}{n},\qquad \tau^\ast=\frac{c_{FP}}{c_{FP}+c_{FN}}\ \text{ if scores are calibrated probabilities} \]Flag an item when \(p\,c_{FN} > (1-p)\,c_{FP}\). With equal costs that is \(p>0.5\); if a miss costs 9 times a false alarm, flag at \(p>0.1\). If scores are not calibrated, sweep thresholds on held-out data instead.
def best_threshold(y_true, scores, c_fp, c_fn):
    """Only observed scores can change the confusion matrix, so sweep those."""
    best = None
    for t in sorted(set(scores)):
        fp = sum(s >= t and y == 0 for s, y in zip(scores, y_true))
        fn = sum(s < t and y == 1 for s, y in zip(scores, y_true))
        cost = (c_fp * fp + c_fn * fn) / len(y_true)
        if best is None or cost < best["cost"]:
            best = {"threshold": t, "cost": cost}
    return best   # tune on a validation split, report on a separate test split

Meanwhile precision falls from 0.845 to 0.199, F1 from 0.881 to 0.328, and MCC from 0.828 to 0.412: 294 false positives for 73 true positives. Same classifier, same threshold. Accuracy and ROC-AUC mislead here; the other three do not.

Watch out
Your metric cannot exceed your label quality. If two humans agree at kappa 0.7 on a taxonomy, a classifier scoring 0.85 against one human's labels is not beating humans; it is fitting one annotator. Measure human-to-human agreement first and report every classifier number against that ceiling. The full decision guide is in Which metric or test, when.
Eval lens
Every number in this chapter is itself an estimate from a finite sample. A precision of 0.85 on 40 flagged items has a 95% interval roughly 0.71 to 0.93. Put intervals on classifier metrics the same way you would on pass rates; see statistics for eval sets and sampling distributions.
