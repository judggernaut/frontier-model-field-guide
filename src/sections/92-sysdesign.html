Basic system design: the building blocks every design round assumes

ML-systems design rounds assume you already know the ordinary parts of a web system: load balancers, caches, databases, replicas, shards, queues. Product-style rounds (a URL shortener, a chat service, a payment flow) test exactly these parts. This appendix is the short version: how a system grows, what each block is for, the numbers to estimate with, and two worked designs.

How a system grows

The same app at five sizes, adding one building block each time.

Every system starts as one machine running the code and the database. Below a few hundred requests per second, that is the right design, and saying so in an interview is a strength.

When one server is not enough, put several identical, stateless copies behind a load balancer. Anything they must remember (sessions, uploads) moves to the database or a shared store.

Reads usually outnumber writes many times over, and a small set of items gets most of them. A cache in front of the database serves those from memory in about a millisecond.

Read replicas copy the primary and take read traffic, at the cost of a little lag. When writes or data outgrow one primary, split the data by a key across several (sharding).

Anything slow or spiky (sending email, encoding video, counting clicks) goes on a queue. The user gets an answer immediately and workers catch up. Because a message can be delivered twice, the workers must be idempotent.

Plain wordsA bakery that gets popular

One baker with one oven works until the queue goes out the door. Then you hire more bakers behind one counter (a load balancer), put the bestsellers on a shelf by the till so nobody has to bake them again (a cache), keep a copy of the recipe book in every kitchen (replicas), split the order book by customer surname (sharding), and take catering orders on a clipboard to bake later (a queue). Every system-design question is this bakery at a particular size, and the interview is about which of these you need, and why, at that size.

For leadersReviewing a design document
  • Is every component justified by a number? Requests per second, data size, latency target. A cache with no stated hit rate, or sharding at 50 GB, are signs of pattern-matching.
  • What is the consistency promise to the user? "You always see your own write" and "everyone sees the same thing within a second" cost very different amounts.
  • What happens when each box dies? Retries need idempotency; queues need a dead-letter path; the database needs a failover plan with a stated data-loss window.
  • What is the simplest version that meets the requirement? Over-engineering is the most common reason strong engineers fail design rounds.

The method in six steps

  1. Requirements (5 min). Functional: the three or four things users do. Non-functional: scale (daily users, requests per second at peak), latency, availability, consistency, durability. Write down what is out of scope.
  2. Estimates (5 min). Peak QPS, storage per year, bandwidth, read-to-write ratio. These decide everything else.
  3. API and data model (5 min). The endpoints with their inputs and outputs; the tables or documents and their keys. The key you partition by is the most important decision in the data model.
  4. High-level design (10 min). Client → load balancer → stateless service → cache → database, plus queues and workers for anything slow. Walk one request through it.
  5. Deep dives (15 min). The two places the estimates say will break: the hot read path, the write throughput, a consistency requirement, fan-out.
  6. Failures, scale and recap (5 min). What breaks at 10×, how you detect and recover from each failure, the one-sentence summary.

Under the hoodConsistency, idempotency, and why retries need both

With replicas, a network partition forces a choice: keep answering and risk stale or conflicting data (availability), or refuse until the partition heals (consistency). That trade is the CAP theorem; in practice the everyday question is latency against freshness, and most products pick per feature: strong consistency for balances and inventory, eventual consistency for feeds, counts and search.

Networks lose responses, so clients retry, so the server sees the same request twice. An idempotency key (a client-generated ID stored with the result, with a unique constraint) makes the second attempt return the first result instead of charging twice. Queues deliver at least once for the same reason. "Exactly once" in practice means at-least-once delivery plus idempotent processing.

\[ \text{servers} \approx \frac{\text{peak QPS}}{\text{QPS per server}\times \text{target utilisation}}, \qquad \text{cache memory} \approx \text{hot items} \times \text{bytes per item} \]Target utilisation around 0.5–0.7 leaves room for spikes and for losing a server. The hot set is often 10–20% of items.

Worked: a URL shortener

Worked problem

Requirements. Create a short link for a long URL; redirect a short link; optional expiry and click counts. 100M new links a month, reads 100× writes. Redirect p99 under 50 ms. Links never collide and never change.

Estimates. Writes: 10⁸ ÷ (30 × 86,400) ≈ 40/s average, call it 200/s peak. Reads: about 4,000/s average, 20,000/s peak. Storage: 10⁸ × 12 months × 5 years × ~500 bytes ≈ 3 TB. Keys: 7 characters of base62 give 62⁷ ≈ 3.5 × 10¹² codes, plenty.

Key generation. Hashing the URL and truncating risks collisions you must check for. Simpler: a counter (or pre-allocated ID blocks per server, so there is no single bottleneck) encoded in base62. If codes must not be guessable, encode a random 64-bit ID and retry on the rare collision under a unique constraint.

Design. Stateless API servers behind a load balancer. POST /links writes (code, url, owner, expiry) to a key-value store or a sharded relational table keyed by code. GET /{code} checks Redis (cache-aside, most traffic hits a small hot set), falls back to the store, returns a 301 (cacheable by browsers, fewer hits for you, but you lose click counts) or 302 (every click reaches you). Click events go onto a queue and are counted asynchronously, never in the redirect path.

Deep dives. A viral link: hot key in the cache; replicate it or keep a small in-process cache on each server. Abuse: rate-limit creation per user, scan URLs against a blocklist asynchronously. Expiry: a TTL on the cache entry and a periodic sweep in the store.

Worked: a rate limiter for an API

Worked problem

Requirements. Limit each API key to 100 requests per minute with short bursts allowed, across 50 API servers, adding under 2 ms.

Algorithm. Token bucket: each key has a bucket of capacity C that refills at r tokens per second; a request takes a token or is rejected with HTTP 429 and a Retry-After header. State per key is two numbers (tokens, last refill time), updated lazily on each request: tokens ← min(C, tokens + r × elapsed).

Where the state lives. In each server's memory is fast but lets a key use 50× its limit across 50 servers. A shared Redis with an atomic script (read, refill, decrement, write in one step) gives a global limit for about 1 ms. A hybrid gives each server a local share and syncs periodically, trading accuracy for latency.

Failure. If Redis is down, fail open (serve, protect availability) for normal endpoints and fail closed for expensive or abusable ones. Say which, and why.

Principal asks
What is the read-to-write ratio, and which path did you optimise? Which data needs strong consistency, and what does the user see during a failover? How do retries avoid double effects? What is the first component to fall over at 10× load, and how will you know before users do?
